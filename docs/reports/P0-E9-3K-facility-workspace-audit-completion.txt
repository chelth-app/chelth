P0-E9-3K — FACILITY WORKSPACE AUDIT & COMPLETION
CHELTH — Healthcare Workforce Operations
Date: 2026-10-11
Branch: p0-e8-visual-implementation (uncommitted; not deployed)

Summary
-------
Audit verdict: facility users already had a real facility-oriented workspace
(option A, not an agency workspace with items hidden), built in P0-E8-S4 and
QA-F1. It had its own nav, Overview, Staffing requests, request detail with
"who is coming" and per-shift attendance, Sign-off, Messages, and facility
projections in the database. The gaps were:
- entry: a facility-only user saw the general gateway, including "Create a new
  agency";
- no facility view of the workers serving the facility across shifts;
- no facility Attendance page;
- no facility Compliance page (shared compliance was a long list buried in the
  Overview);
- an incomplete Overview: no "Request staff" action and no today/attention
  counts.
This phase closes those gaps with one new audited database projection and
three facility pages. It reuses every existing model; no second request,
compliance or attendance model was created.

====================================================
1. CURRENT FACILITY ENTRY BEHAVIOUR
====================================================

Before: sign-in → /app gateway for all non-worker accounts. A facility-only
user saw an organisation card plus a "Create a new agency" panel, and the
facility Overview linked back to it.
Now (facilityOnlyOrganisations):
- one facility (every visible membership is a facility membership with a
  role) → /app redirects to that facility's Overview, and the Overview hides
  "All organizations" (there is nothing to go back to);
- several facilities → the gateway lists them, with no agency-creation panel;
- agency, mixed agency + facility, role-less or new users → unchanged
  gateway (mixed users keep the switcher and chooser);
- a pending invitation or a notice still shows the gateway first.
Presentation only; every page keeps its own server gate.

====================================================
2. CURRENT NAVIGATION
====================================================

Facility nav (buildWorkspaceNavigation, capability-driven, same predicate as
each page gate):
  Overview · Staffing requests (shift.view) · Coverage (shift.view) ·
  Attendance (attendance.view) · Compliance (credential.view) ·
  Sign-off (timesheet.facility_signoff) · Messages (message.view) · Settings
Agency items (Operations, Shifts, Workforce, Facilities, Finance) are never
listed in a facility workspace, even with every capability (unit-tested), and
their routes 404 for facility organisations (E2E).
"Sign-off" is kept rather than "Timesheets": it is the approved, tested
label, and it is the facility's whole timesheet role.

====================================================
5. STAFFING REQUEST FLOW
====================================================

Audited and unchanged: submit_facility_shift_request (relationship, location,
discipline, local date, start/end, headcount, instructions, reference),
facility list with status and fill filters, drawer, detail, withdraw. Status
labels: Requested (submitted), Open with Unfilled / Partially filled / Filled,
Canceled / Cancelled (workspace spelling), Completed. Lifecycle E2E: facility
submits in the UI → agency opens and assigns → worker accepts → facility
Coverage shows the worker as Accepted.
Unit: not part of the facility request (the agency sets it on the shift);
see §24.

====================================================
6. SHIFT VISIBILITY
====================================================

Facility "shifts" are its staffing requests: the same facility projection
(list_facility_shifts / _page), scoped by the linked facility organisation,
relationship capability, non-ended relationship and non-draft shifts. Fields:
date, start/end, role, location, agency, status, fill, instructions. Workers
and attendance appear on each request and now on Coverage and Attendance. No
pay, bill or pricing fields exist in any facility projection (pgTAP F check).

====================================================
7. WORKERS / COVERAGE
====================================================

New /coverage (facility only, shift.view) with views Today / Next 14 days /
Last 7 days, backed by public.list_facility_coverage (§22). Rows: worker
display name, role, shift date and time (facility local), location, agency,
response (Awaiting response / Accepted), readiness for this facility when not
ready (upcoming only), and attendance state with attendance.view. Each row
links to its staffing request. Only workers assigned to this facility's own
shifts; never other facilities, pay, contact details or agency notes. Empty
states: "Workers assigned to this facility will appear here. Request coverage
when you need additional staff."

====================================================
8. COMPLIANCE
====================================================

New facility branch of /compliance (credential.view + relationship.view):
- per active agency relationship, the workers that agency has shared
  (list_shared_worker_compliance, the existing audited projection evaluated by
  the one engine against this facility's requirements);
- readiness, each requirement's status and "valid to" date;
- KPIs: shared, ready, needs attention.
No documents, credential numbers or unshared workers. Facility users still
cannot manage requirements: facility roles do not hold
credential.requirements.manage, and requirements live on the agency's facility
record. Supervisors (no credential.view) get a 404.

====================================================
9. ATTENDANCE
====================================================

New facility branch of /attendance (attendance.view): today's workers at the
facility's own shifts, including overnight shifts still running. Each shows
Not started / Clocked in / On break / Completed / Needs review, plus "Not
checked in" when an accepted worker has not clocked in after the start. KPIs:
Scheduled today, Checked in (on break), Completed, Needs attention.
Derived states only: no coordinates, accuracy, distance or geofence evidence,
and no review or correction tools (agency-only). The agency attendance page
and its record/evidence routes still 404 for facilities.

====================================================
10. TIMESHEETS
====================================================

Audited: facilities sign off or dispute agency-approved entries
(facility_decide_timesheet_entry; timesheet.facility_signoff: Admin and
Supervisor). Surfaced as "Sign-off" in the nav, an Overview KPI and a panel.
No pay, margin, pricing or payroll data (existing NO_LEAKS E2E checks). No new
approval semantics.

====================================================
11. MESSAGING
====================================================

Unchanged model: agency ↔ facility threads per relationship and shift; worker
↔ agency only; no worker ↔ facility thread. Admin and Scheduler hold
message.view/send; Supervisor does not (nav hidden, route 404, tested).
Added: unread count on the Overview.

====================================================
12. SETTINGS
====================================================

Facility Settings = Organization (profile; organisation.manage to edit),
Team & Permissions (view; invite/roles for Admin), Security. Agency sections
(Attendance & Geofencing, Payroll, Rates, Compliance) are refused for facility
organisations (canOpenSection; E2E 404 for settings/rates, payroll,
compliance). Locations, arrival guidance, worker contact and facility photo
are agency-maintained on the agency's facility record today (§24).

====================================================
13. CUSTOM REQUIREMENT INTEGRATION (P0-E9-3J)
====================================================

Agency-owned custom types are used in facility-specific requirements on the
agency's facility record (3J; tested). Facility users see custom requirements
in their Compliance view by name, exactly like standard ones (same engine,
same projection). Facility users do not select or create types: they hold no
requirement-management capability, and the relationship model gives them no
requirement authorship. Facility-owned custom types are a later feature (§24).

====================================================
14. PRIVACY BOUNDARIES
====================================================

Facility-facing fields (all pages): worker display name, role, shift times,
location, agency name, response, readiness, derived attendance state,
requirement name/status/valid-to, and sign-off entries (worked time).
Never: home address, personal email or phone, pay or bill rates, payroll,
margins, pricing, raw geolocation or geofence evidence, credential documents
or numbers, internal notes, other facilities or other agency relationships.
Enforced in the projections (pgTAP F: no coordinate/pay/contact/note columns)
and asserted in E2E (NO_LEAKS pattern on every new page).

====================================================
15. TENANT ISOLATION
====================================================

list_facility_coverage scopes every row by: the caller's facility organisation
is the shift's linked facility, the relationship is not ended, the caller
holds shift.view on that relationship (authz.has_relationship_capability), the
shift is not a draft. Attendance columns need attendance.view on the same
relationship. Agency organisations, workers and other facilities get CH403.
Tested:
- pgTAP 320: Gamma sees only Mercy; Delta only Beta Client; the unlinked
  Riverside never appears; cross-facility, agency and worker calls → CH403;
- E2E: a second facility admin gets 404 on every facility route of the first
  facility (overview, requests, coverage, attendance, compliance, messages,
  sign-off) and CH403 from the RPC directly.

Root cause — facility-workspace (genuine defect, not a race)
-------------------------------------------------------------
The route file src/app/app/organisations/[organisationId]/(workspace)/
coverage/page.tsx was never committed. .gitignore line 31 "coverage/" (meant
for Vitest's root coverage report) is unanchored, so it matched the route
directory (workspace)/coverage/. `git check-ignore` confirmed it, and
`git ls-files` showed only facility-coverage-table.tsx. CI builds from the
checkout, so /coverage did not exist there. A production deploy of #35 as
pushed would also have shipped without the Coverage page. Local runs passed
because the file existed on disk.
Not a projection race, fixture collision or date issue: the request,
assignment and acceptance all succeeded (200s in the trace) before the 404.

Root cause — overview-fidelity (test date dependency)
------------------------------------------------------
The suite's open places are created from isoDay(1) (UTC tomorrow). The earlier
Sunday fix (09dcb73) changed only the first calendar visit to
week=isoDay(1). The viewport loop (line 576) and the phone-sheet step
(line 583) still opened "?view=calendar" with no week, which means the
server's current week. CI ran at 23:48 UTC on a Sunday: the current week
(Oct 5–11) held none of the fixture shifts (Oct 12 onwards), so the agenda
list was not rendered. Locally the clock was already Monday (UTC+2), so the
current week contained the shifts and the bug was hidden.

Changes
-------
Product code: no change. The page is the same 3K Coverage page, now tracked
  in git.
Repository config: .gitignore "coverage/" → "/coverage/" (root-anchored,
  with a comment). Vitest coverage output at the repo root is still ignored
  (verified with git check-ignore on a root coverage/ file).
Test code: overview-fidelity.spec.ts uses one `fixtureWeek` URL
  (week=isoDay(1)) for every calendar visit. No assertion was removed or
  weakened, and no retries, skips, soft asserts or timeout increases were
  added. facility-workspace.spec.ts is unchanged.
No migration.

Why the fix is deterministic
----------------------------
- Coverage: the route is in the repository, so every checkout (CI, Vercel)
  builds it; it no longer depends on files left on a developer disk.
- Calendar: every visit opens the week containing isoDay(1). The fixture's
  first open places are created on isoDay(1), so that week holds them on any
  weekday, at any hour, in any server or runner timezone. Nothing depends on
  the "current week" any more.
