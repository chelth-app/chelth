3. COMPLIANCE HEADER
--------------------
- "Compliance". The subtitle comes from the reference: "Monitor workforce
  credentials, expirations, and readiness across your organization."
- The right side holds the real "Add requirement" action (requirement
  managers only; it scrolls to the existing form) in the locked
  primary-CTA treatment.
- The reference's "Add Credential" is not offered: agencies don't create
  credentials; workers do.
- The existing step-up notice for requirement changes is kept.


4. KPI AREA (region "Credential readiness summary"; each card filters)
---------------------------------------------------------------------
Counts are of readiness-engine results, grouped by engine reason:
- Up to Date: MET.
- Expiring Soon: EXPIRING_SOON (inside the requirement's warning window).
- Needs Review: UNVERIFIED_CREDENTIAL and DOCUMENT_NOT_CLEARED
  (verification or security scan pending).
- Missing: MISSING_CREDENTIAL, CREDENTIAL_NOT_SHARED, NOT_SUBMITTED,
  DOCUMENT_MISSING.

The remaining blocking reasons (expired, rejected, insufficient validity,
wrong jurisdiction, worker not active, discipline not set) are counted in
the Missing card's supporting line and filterable by Status.

No scores or ratings.


5. FILTERS (form "Filter credentials")
--------------------------------------
- Professional, Type ("All credential types"), Status (register groups),
  Expiration (30 / 90 days / expired, from the engine's effective expiry
  date) and Search (worker or credential): these narrow the loaded results
  on screen only.
- Facility re-runs the same engine read with that facility
  (worker_readiness / evaluate_worker_compliance with
  p_agency_facility_id), so facility add-on requirements appear with scope
  = that facility. This is the worker record's existing per-facility check.
- Show / Clear filters. Paging uses the Workforce pager (10 per page).


6. COMPLIANCE TABLE ("Credential Register"; region "Credential register table")
-------------------------------------------------------------------------------
- One row per engine result: worker × requirement, from getReadiness. This
  is the same loader and gate (compliance.view) as Workforce and the worker
  record, so "Missing" rows are real unmet requirements, as in the
  reference.
- Columns:
  - Professional: avatar, linking to the worker record;
  - Role: disciplines;
  - Credential;
  - Status: the engine reason label;
  - Verification: this agency's latest decision, from
    list_agency_worker_credentials;
  - Expires: date plus days remaining;
  - Scope: Agency baseline or the facility;
  - ⋯ "Credential Details".
- 48 px rows; the selected row gets the teal inset and a mint fill. At
  1536 px and wider with the drawer open, the work area contracts.
- The existing "Agency baseline requirements" table and "Add a baseline
  requirement" form follow below, unchanged in behaviour.


7. CREDENTIAL STATES
--------------------
Engine wording only (COMPLIANCE_REASON_LABELS): Requirement met, Expires
soon, Awaiting verification, Document awaiting security scan, Missing, Not
shared, Not yet submitted, Expired, Verification rejected, and so on.
Verification uses VERIFICATION_LABELS (Under review / Verified / Rejected).

Tones:
- green: met;
- amber: expiring, not submitted;
- blue: awaiting verification or scan;
- red: missing, expired, rejected;
- slate: worker-level.

The rules were not simplified.


8. EXPIRATION TREATMENT
-----------------------
- The engine's effective expiry date, formatted as a calendar date with no
  timezone shift.
- Days remaining: whole days from today (UTC), via the existing
  daysUntilDate.
- The days-remaining note is amber when the engine says EXPIRING_SOON and
  red once expired.
- The drawer has an Expiration section; the record shows Issued / Expires
  per version.
- No percentage bar: the reference's "67%" would need a validity span the
  register row does not carry.


9. CREDENTIAL DRAWER ("Credential Details"; canonical drawer)
-------------------------------------------------------------
- Identity: worker (21 / 700), the credential as record type, disciplines,
  and the status chip.
- Meta rows: requirement scope; valid-to date.
- Tabs:
  - Overview:
    - Credential Details (KeyValueList: credential, status, requirement,
      jurisdiction, expiration date, latest version);
    - Credential Document (soft tile: cleared / not cleared / no credential
      on file);
    - Verification;
    - Expiration.
  - Requirements: the worker's full engine coverage for the same
    evaluation.
- Actions:
  - "Review Credential" (credential.view, when a shared credential
    exists): opens the credential record.
  - "View Professional": the worker record.
- "Request Update" is not offered: Chelth has no request or messaging flow.


10. CREDENTIAL RECORD PAGE (canonical arrangement)
--------------------------------------------------
Route: …/workforce/[workerId]/credentials/[credentialId]. Same reads and
gates as before.

1. Breadcrumb: the worker.
2. Title: the credential type. Description: jurisdiction · authority ·
   number (when RLS allows).
3. Status: the latest own verification badge (or "Withdrawn by the
   worker"), plus RecordMeta "Version n is current".
4. SectionTabs "Credential record sections":
   - Summary · Versions · Verification · Requirements (compliance.view) ·
     Sharing and history.
5. AAL2 StepUpNotice: unchanged.
6. Summary panel (KeyValueList).
7. Versions and documents.
8. Verification: the existing VerificationForm under the same conditions,
   or a truthful status note.
9. Requirement coverage: engine results for this credential type.
10. Sharing and history: this agency's share only, and this agency's
    decision history.


11. VERSIONS
------------
- Submitted versions, newest first. Labels: "Current" for the latest
  submitted version, "Earlier version" for the rest.
- Each shows issued, expires and submitted dates, plus its own verification
  badge.
- Copy: "Versions are kept as submitted; a new version never overwrites an
  earlier one."
- No edit or delete affordance.


12. VERIFICATION
----------------
- VerificationForm is unchanged: "Record decision", credential.verify
  (AAL2), and facility scope for facility-scoped types.
- The decision history lists only this agency's decisions, with rejection
  reasons.
- The drawer shows the agency's latest decision only.


13. SCANNER STATE
-----------------
- Documents show DocumentStatusBadge: Uploading / Awaiting security scan /
  Cleared / Rejected / Quarantined.
- "Open document" appears only for clean documents and credential.review.
  It uses the existing audited signed-URL gate (OpenDocumentButton).
- The drawer says "Document cleared" only when list_agency_worker_credentials
  reports a clean document on the latest submitted version. Otherwise:
  "Evidence waiting for, or failing, the security scan is never treated as
  verified."
- Truthfulness fix: document rows are readable only with credential.review
  at AAL2, so without that access the record says "Documents are listed for
  reviewers after verification with an authenticator app" instead of
  claiming none are attached.


14. REQUIREMENT COVERAGE
------------------------
- Register rows, the drawer's Requirements tab and the record's coverage
  panel show only getReadiness / evaluate_worker_compliance results.
- Nothing is computed client-side; filters only narrow.


15. SHARING
-----------
- The record shows only this agency's active share ("Shared with <agency>
  since …"). Other agencies' shares and decisions are filtered out.
- Visibility is still decided by RLS: the route returns 404 unless the
  credential is shared with the caller's agency.

18. INTENTIONAL PRODUCT / DATA DIFFERENCES
------------------------------------------
- Rows are requirement results, not stored "credential records":
  - there is no agency-wide credential table;
  - Missing is a requirement state;
  - a credential that no requirement uses doesn't appear in the register,
    but stays on the worker record.
- The column set differs from the reference:
  - Issued is not in the register projection, so it isn't a column; it is
    on the record.
  - Verification replaces it.
  - Photos and per-row checkboxes are not shown: there is no photo data and
    no bulk action.
- Not offered: Add Credential (worker-only), Request Update (no flow),
  Credential Number in the drawer (restricted; shown on the record when RLS
  allows), the issuing-authority row in the drawer, the uploaded filename,
  the expiration percentage bar, and the drawer activity feed (the decision
  history is on the record).
- Requirement management stays on this page below the register, as before.
- Frame: this reference's sidebar is narrower (about 198 px) than the
  locked shell (214 px), so content sits about 24 px further right in the
  overlays (03 / 11). The composition and order match.
- At docked 1536:
  - KPI labels wrap;
  - the filter row wraps;
  - the register scrolls horizontally inside its region.
  This follows from the locked geometry.
- QA data: the fixture agency (BLS baseline, 8 workers; Fay's BLS expires
  in 20 days). The admin is not stepped up, so step-up notices show.
