1. EXECUTIVE SUMMARY
--------------------
Chelth's application layer is unusually well hardened for this stage:
- deny-by-default RLS on all 81 tables;
- 351 SECURITY DEFINER functions, all with a pinned search_path;
- no anon grants and no service role in the app;
- AAL2 on every privileged capability; maker-checker on finance;
- private, policy-checked storage with 60-second signed URLs;
- server-authoritative attendance; an append-only audit trail;
- 1,331 pgTAP security assertions;
- every suite green.

The functional golden path is implemented and tested end to end locally.

Chelth cannot yet run a pilot with real people, because the parts OUTSIDE
the repository have not been built or verified:

1. There is no production malware scanner. In production every uploaded
   credential document stays "scanning" forever (deliberately
   fail-closed). As a result:
   - document-backed credentials can never be verified;
   - readiness can never pass;
   - no worker can become eligible for a shift.
   The golden path is broken in production.
2. Auth email delivery (sign-up confirmation, password reset) depends on
   hosted Supabase SMTP, and nothing shows custom SMTP is configured. The
   built-in sender is rate-limited and is not meant to reach arbitrary
   recipients, so real agencies and workers may be unable to confirm
   accounts or recover passwords.
3. No hosted environment has been verified end to end: environment
   variables, applied migrations, cron, Vault, the notifier role, Resend
   and auth templates. No production smoke test has been run.
4. There is no error monitoring or alerting, no verified backup /
   restore, no privacy notice or terms, no support channel, and no
   real-device certification of check-in / out.

None of these is a flaw in the application's security model. They are
infrastructure, configuration, operations and legal work, plus one
integration (scanning).

Recommendation: NOT READY FOR PILOT. With about five focused phases (section
25), Chelth can reach READY FOR CONTROLLED EXTERNAL PILOT.

3. P0 BLOCKERS — CANNOT PILOT
-----------------------------
P0-1  No production malware scanner. The golden path cannot complete.
      [INFRASTRUCTURE + CODE]
      - docs/security/CREDENTIAL_DOCUMENT_SECURITY.md §3: "There is no
        production scanner yet: production uploads stay `scanning` and
        therefore cannot satisfy requirements or be verified."
      - The only scanner is scripts/local-scan-documents.mjs (it refuses

      - The current state is safe (fail-closed: nothing is falsely
        clean), but every requirement whose credential type requires a

        would defeat the trust gate. It must NOT be done as a

      function → scanning service → internal.record_document_scan_
      result, with the quarantine move and an owner notice), run as an
      approved privileged role, not the web app.

P0-2  Auth email delivery to real users unverified. [CONFIGURATION]
      - Sign-up requires confirmation (enable_confirmations).
      - Password recovery and email change are email-only.
      - supabase/config.toml is local-only; [auth.email.smtp] is commented
        out.
      - Nothing in the repository or the reports shows custom SMTP on the
        hosted project.
      - P0-E3-S2B found the hosted recovery template had drifted. The
        required template state was documented, but "the hosted values …

      Without custom SMTP and the Chelth templates (confirmation.html,
      recovery.html, email_change.html with the
      /auth/confirm?token_hash=… link), agencies and workers cannot
      reliably confirm accounts or reset passwords.
      Fix:
      - configure custom SMTP (e.g. Resend SMTP) with SPF / DKIM / DMARC
        on the sending domain;
      - apply and read back the three templates, Site URL and redirect
        allow-list;
      - raise the auth email rate limits for the pilot;
      - smoke-test sign-up, confirmation and recovery on real mailboxes.

9. CREDENTIAL / DOCUMENT SAFETY
-------------------------------
Exact current condition:
- Upload:
  1. The server action validates the name, declared MIME, size and
     extension match.
  2. begin_credential_document_upload checks ownership, a draft version,
     ≤5 documents, 50 per day, MIME and size → upload_pending.
  3. A signed upload URL is minted for exactly that path.
  4. The browser uploads directly to Storage.
- Completion: the server downloads the object as the user and checks:
  - size = declared ≤ 10 MiB (bucket-enforced too);
  - magic bytes match pdf / jpeg / png;
  - SHA-256 → scanning (or rejected, and the bytes are removed).
- Scan state machine: upload_pending → scanning → clean | quarantined |
  rejected (trigger-enforced). No API role can execute
  record_document_scan_result.
- Production scanner: NONE. Local / test only. Placeholder logic never
  runs against hosted hosts.
- Fail mode: fail-CLOSED. Pending / scanning documents:
  - are not evidence;
  - cannot be opened by reviewers;
  - cannot be verified.
  The owner can open their own scanning document (their own bytes only).
- Quarantined / rejected: unreadable by reviewers (RLS, Storage policy
  and the RPC); the owner sees the state.
- Retry: no scanner, so no retry logic yet.
- Audit: document access, denial, upload and verification are audited
  (never paths or URLs).
- Pilot impact: P0-1.


10. EMAIL / NOTIFICATIONS
-------------------------
- Outbox: one row per recipient in the same transaction as the domain
  event; ids and codes only (no address, body or token).
- Claim: FOR UPDATE SKIP LOCKED, batch ≤ 100, 120-second lease, claim-token
  completion (stale_claim protection).
- Retries: backoff 1 min / 5 min / 30 min / 2 h; final after 5;
  deliver_until expiry.
- Idempotency: Resend idempotency key per outbox row (24-hour window);
  a unique pending row per (event, subject, recipient).
- Delivery records: sent_at and provider_message_id on the row; final
  failures are audited; /operations lists failed / retrying deliveries per
  tenant.
- Local verification: pgTAP 140, integration (notifications-operations),
  e2e.
- Hosted execution: NEVER VERIFIED. No production smoke test exists.
- Auth email (Supabase GoTrue): separate path; see P0-2.
- In-app notifications: none (no recipient-scoped inbox exists).


11. WORKER MOBILE
-----------------
Code verified (e2e on Pixel 7 emulation plus desktop):
- sign-in; My Shifts; offers / assignments; the Shift Details sheet;
- clock in / break / clock out; attendance captured; timesheet handoff,
  submit;
- credentials; upload / open own document.

Assumptions and risks:
- Browser web app (responsive) plus a web manifest; no service worker:
  - not offline-capable;
  - installable only as a basic home-screen bookmark;
  - no push.
- Geolocation: one getCurrentPosition per action, enableHighAccuracy,
  15-second timeout, maximumAge 0; never watched. All errors map to "no
  reading" (P2-3).
- Permission denied: the server then refuses where location is required
  (worker guidance shown), or records it with review.
- Duplicate submit: the button is disabled while pending, and the server
  refuses a second clock-in / out (CHT09 / CHT11).
- Reload: state is server-derived (safe).
- Safari risks:
  - permission prompts per site and session;
  - precise location can be toggled off ("Precise: Off" gives
    kilometre-level accuracy, which becomes low_accuracy);
  - a background-tab timer can stall.
- Android Chrome risks:
  - battery saver / location mode;
  - a cold GPS fix exceeding 15 seconds indoors.
- Native mobile: not recommended. No demonstrated blocker; the web flow
  is complete.
