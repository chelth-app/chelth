1. EXECUTIVE SUMMARY
======================================================================
The shared operational visual language now exists as owned primitives in
src/components/ui, composed from the existing tokens:

  - PageHeader, KpiFilterCard / KpiFilterGroup;
  - FilterBar / FilterField / FilterSelect;
  - DataTableRegion, DataTable (+ Head / HeaderCell / Row / Cell) and
    DataTablePagination;
  - StatusChip (six semantic tones), SectionTabs;
  - DetailDrawer / DetailDrawerTrigger, KeyValueList, ActivityTimeline;
  - EmptyState, plus restyled ErrorState / LoadingState.

The repeated table-region problem is fixed structurally:
  - all 30 hand-written scroll regions now use DataTableRegion
    (relative overflow-x-auto, named, focusable);
  - a unit test fails if a raw one reappears;
  - every axe checkpoint in the E2E suite now also asserts no page-level
    horizontal overflow, which runs at 412 px on the mobile project.

Status colours now derive from the brand semantic palette. Domain status
badges render through StatusChip.

The Overview no longer repeats the sidebar.

Adoption is deliberately conservative, on representative pages:
  - Overview cleanup;
  - Attendance (operational P3 list, with the P5 drawer);
  - Pricing (P3-F finance list with route tabs);
  - the priced-timesheet record (detail);
  - a workspace error boundary and empty states.

No database, migration, RLS, capability, Server Action, RPC, query or
business logic changed.

3. SHARED PRIMITIVE ARCHITECTURE
======================================================================
Everything lives in src/components/ui (exported from its index), next to
Button, Card, Dialog and FormField. There is no second component system and
no new dependency.

Server-compatible primitives (no client JS):
  - PageHeader;
  - KpiFilterCard;
  - FilterBar;
  - DataTable*;
  - StatusChip;
  - SectionTabs;
  - KeyValueList;
  - ActivityTimeline;
  - EmptyState / ErrorState / LoadingState / StateIcon.

The only new client component is DetailDrawer (+ Trigger). Like the existing
Dialog, it is built on the native modal <dialog>, which is CSP-safe and
injects no inline styles.

Not built, by design:
  - SearchField: no page-local search exists, and the prompt makes it
    conditional.
  - ActionMenu: row actions stay as visible inline buttons. Hiding them
    behind a menu would change product behaviour, and no safe menu
    primitive exists yet.

4. PAGEHEADER
======================================================================
Slots:
  - title, rendered as the page's one h1;
  - description;
  - back (breadcrumb or back link);
  - meta (chips and labels);
  - primaryAction;
  - secondaryActions.

Typography:

    down (28/36), which the typography document's mobile rule allows.
  - Supporting copy: Inter 16/24, muted.

It is compact (no hero), and actions sit top-right from sm and stack below.

Adopted on:
  - Overview;
  - Attendance;
  - Pricing;
  - the priced-timesheet record.

======================================================================
5. KPI CARDS
======================================================================
KpiFilterCard: icon tile (decorative), value (Manrope 26/30, tabular),
label (Inter 14/20) and optional supporting text.

Behaviour:
  - It is a Link (filter or section shortcut) or a static figure.
  - Active state: aria-current="true", a 2 px Deep Teal border and a
    visible "Showing" marker, so it is not colour-only.
  - No charts, sparklines or deltas.
  - KpiFilterGroup is a named region, laid out as 1 column on phones, 2 on
    tablets and 4 on wide screens.

Adopted on Attendance with real counts the page already loads:
  - Scheduled;
  - Needs review;
  - Correction requests;
  - Open exceptions (with an urgent count).
Each card links to its section with an anchor. The page has no
status-filter parameter, so none was invented.

6. FILTERBAR
======================================================================
FilterBar is a named native GET form, so filters stay in the URL and work
without JavaScript.
  - Labels sit above controls (P3-F).
  - Submit wording is kept per page.
  - Optional clear/reset link and an actions slot.
  - Wraps on phones.
  - FilterField and FilterSelect wrap the existing Label and native Select.
  - There is no global search.

Adopted on Attendance:
  - Same field names, ids, labels and submit text ("Show").
  - Adds a "Today" reset link: the existing unfiltered URL, which already
    means "today at each facility".

======================================================================
7. DATATABLE / DATATABLEREGION
======================================================================
DataTableRegion:
  - role="region", tabIndex=0;
  - a REQUIRED accessible name, enforced by the type system
    (aria-label | aria-labelledby);
  - "relative overflow-x-auto" plus the existing card border and surface.

DataTable components standardise:
  - text size;
  - header styling (12 px, muted, Cloud background);
  - cell density (px-3 py-2.5);
  - row hover;
  - `selected` rows (aria-selected + Mint Mist);
  - right-aligned tabular `numeric` cells.

Cell content stays page-specific; there is no column abstraction.

DataTablePagination is a cursor pagination nav with a name, an optional
summary and 44 px previous/next links. The app pages by cursor, so there are
no numbered pages.

Sticky headers are not applied. Inside a horizontal scroll container a
sticky top header is relative to the region, not the page, so it would not
stick. Documented in §21.

8. MOBILE OVERFLOW FIX
======================================================================
Cause (S0): sr-only header text is position:absolute. Inside a
non-positioned overflow container it escaped to the page, causing
page-level horizontal scroll (817 px measured in P0-E7-S3).

Fix:
  - All 30 regions were migrated mechanically to <DataTableRegion>, with
    the same names and children; only the wrapper changed. S0 counted 22;
    the financial adjustment tables added more.

    Area                                   Regions migrated
    -------------------------------------  -----------------------------
    attendance list / record / evidence    3
    timesheets page                        2 (+ entries-table)
    shift detail, staffing-request detail  1 each
    workforce                              1
    rates                                  2
    pricing list / priced record           2
    organisation hub                       1
    payroll list / batch / adjustment      2 / 2 / 1
    invoices list / draft / adjustment     2 / 1 / 1
    financial-tables.tsx                   3
    adjustment-tables.tsx                  4

  - The local TABLE_REGION class constants were removed.

Guards:
  - Unit: a structural test fails if any src file with a <table> uses
    overflow-x-auto outside DataTableRegion.
  - E2E: every spec's expectNoA11yViolations helper now also asserts
      document.documentElement.scrollWidth <= clientWidth.
    It therefore runs at every existing axe checkpoint, with real data, on
    desktop and on Pixel 7 (412 CSS px). Covered:
      - hub;
      - attendance list, record and drawer;
      - timesheets;
      - shift and staffing-request pages;
      - workforce and facilities;
      - rates and pricing (list and record);
      - payroll and invoices (lists, batches, drafts, adjustments);
      - compliance;
      - operations.
  - Mobile content was not redesigned.

9. STATUS SYSTEM
======================================================================
StatusChip has six tones:

  Tone       Meaning
  ---------  -----------------------------------------------------
  neutral    inactive, draft, not required, closed without issue
  info       in progress, waiting on someone else
  success    done, verified, signed off, filled
  warning    caution, partial, expiring, declined
  danger     failed, blocked, disputed, cancelled with impact
  attention  needs an operator's action now (Critical + Warning, an
             orange)

Visual: a soft pill with a decorative leading dot. The text is always the
meaning.

Tokens (globals.css, @theme inline), derived from brand.css:
  - soft background = brand colour 12% on white;
  - foreground = 62% brand + 38% Ink;
  - indicator = the brand colour.

Text contrast on its own soft background:

  Tone       Ratio
  ---------  -----
  success    6.35
  warning    5.55
  danger     6.91
  info       6.22
  attention  6.20
  neutral    6.35

The destructive-button danger colour is now Critical: white text 5.14:1,
hover 6.68:1. No reference hex values were imported.

The previous status tones (#dcfce7 etc., recorded as brand drift in B3) are
replaced. Because Badge, notices and form errors use the same soft tokens,
they now also render in brand-derived tints.

Consolidation into StatusChip:
  - Attendance, Timesheet / Facility state, Shift / Fill / Assignment /
    Offer, Readiness, Worker, Facility / Relationship, Verification /
    Document, Payroll / Invoice status and AttentionBadge.
  - The domain "brand" tone, used only by approved/locked financial
    statuses and the "open" shift status, maps to info. ADJUSTMENT_REQUIRED
    maps to attention.
  - Inline status badges on adopted pages were converted (Overview member
    status, Attendance, Pricing).

Badge remains for non-status labels (organisation type, role names) and for
inline badges on pages not yet adopted (§21).

10. DETAILDRAWER
======================================================================
DetailDrawer is a native modal <dialog>:

Desktop:
  - right-hand panel with sm / md / lg widths (24 / 28 / 36 rem);
  - the page stays visible behind a light Ink 30% backdrop;
  - header with title, description and a "Close details" button (44 px);
  - scrolling body;
  - footer action stack (primary full width, then secondary).

Phones: a full-height, full-width sheet.

Behaviour:
  - Escape, the close button and a backdrop click all close it.
  - The focus trap and inert background come from showModal().
  - Focus returns to the trigger.

DetailDrawerTrigger owns the open state. Its content is server-rendered and
passed as children, so no data is fetched client-side.

The drawer never replaces a deep-link route. On Attendance each row has a
"Details" button whose accessible name is "Details for <worker>". It opens
the row's facts (status, facility, location, shift, timezone, clock in/out
with location results, needs attention) with "Open attendance record" and
"Open shift" links. The record and shift routes are unchanged.

11. TABS
======================================================================
SectionTabs are navigation tabs: a named <nav> of links with
aria-current="page" and an optional real count. They use underline styling,
44 px targets and scroll inside themselves on phones. They are never
role="tab", because these tabs change the URL.

Adopted on the Pricing queues (Needs attention / Ready for pricing /
Priced), replacing the hand-styled pill links with the same names and URLs.

21. KNOWN GAPS
======================================================================
1. The drawer is modal rather than docked. The P3 reference contracts the
   table beside an open drawer; a docked, non-modal panel needs its own
   focus model. The modal drawer is the safe accessible default.
2. Drawer adoption is limited to Attendance. Other P3 lists will adopt it in
   their domain stages.
3. Sticky table headers are not applied (they do not work inside a
   horizontal scroll region; see §7).
4. Inline <Badge> status usages remain on pages not yet adopted (about 20
   files). They already use the new brand-derived tints; converting them to
   StatusChip is per-domain work.
5. No SearchField (no page-local search exists) and no ActionMenu (row
   actions stay visible).
6. KPI cards on Attendance jump to sections. They are not filters, because
   the page has no status filter parameter, and none was added.
7. Chip text can wrap in narrow table columns. Acceptable; revisit with
   column sizing in the domain stages.
8. PageHeader is adopted on 4 pages. Other pages keep their text-2xl
   headers until restyled.
9. No loading.tsx was added (it would introduce new Suspense boundaries).
10. Role labels on the hub use Badge tone "info", which now renders in the
    brand-derived info tint. This is visually close to a status chip but has
    no dot.
