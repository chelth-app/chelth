1. EXECUTIVE SUMMARY
--------------------
The worker product is now one coherent mobile / PWA experience:
- Today / Upcoming / Past;
- a canonical Shift Details screen with real context (photo or approved
  artwork, address, destination-only directions, unit, parking / arrival
  guidance, an opt-in role / desk contact, engine requirements);
- the check-in → checked-in → check-out → worked-time handoff on that
  screen;
- secure, retained, text-only operational messaging for workers, agency
  staff and facility staff;
- credentials and the PWA from E9-3C.

Everything is server-authoritative, deny-by-default and covered by pgTAP,
integration and E2E tests. All automated validation is green.

The one remaining pilot gate is real-device certification (Android and
iOS), which this session could not perform.


2. S1 ARCHITECTURE FINDINGS
---------------------------
Already present and reused:
- facility addresses;
- shift-level instructions;
- the readiness engine;
- the notification outbox;
- the capability system;
- relationship-scoped cross-organisation access.

Missing:
- units, facility arrival guidance, worker-facing contacts, facility
  images, messaging.

Decisions taken within the invariants:
- the contact is a role / desk, not a personal name;
- arrival guidance is a facility default with the shift instructions as
  override;
- the unit is a nullable shift label;
- images are optional, private, AAL2-uploaded and signature-checked;
- messaging access is derived, not stored (worker ↔ agency, agency ↔
  facility; there is no worker ↔ facility direct thread).

4. SHIFT CONTEXT ADDED
----------------------
The worker projection carries the unit, address, guidance, contact, image
and facility-local date, only while the assignment is active. Past shifts
show their record, not live context.


5. TODAY / UPCOMING / PAST
--------------------------
Facility-local calendar from the server render:
- today includes in-progress night shifts;
- Today shows "Next Shift" when nothing is today, plus "Upcoming Shifts"
  rows.


6. FACILITY IMAGE
-----------------
- Agency "For workers" panel; JPEG / PNG ≤ 2 MB; server signature check.
- Short-lived signed URLs for assigned workers.
- The approved artwork as fallback.
- Not malware-scanned (accepted risk, S1 D4).


7. ADDRESS
----------
The location's own address when recorded, otherwise the facility's. No
duplicate fields.


8. DIRECTIONS
-------------
Destination-only deep link: Apple Maps on Apple devices, Google Maps
elsewhere. No worker or shift data is sent.


9. UNIT
-------
Optional, set by agency schedulers on the shift (audited). Shown on cards,
Shift Details, check-in and threads.


10. PARKING / ARRIVAL
---------------------
Facility defaults plus the existing per-shift instructions, shown together
in "Arrival".


11. WORKER-FACING CONTACT
-------------------------
An opt-in role / desk label and business phone with a tel: Call button. The
site phone / e-mail are never shown to workers.


12. REQUIREMENTS
----------------
The readiness engine per facility, unchanged: valid-until / reason, with a
link to credentials when something needs action.


13. MESSAGING ARCHITECTURE
--------------------------
- conversation_threads: worker | facility, with optional shift / request
  context.
- messages: append-only text, server time, an idempotency key.
- message_receipts: last-read position.
- RPCs to open, send (idempotent, rate-limited), mark read, list, get and
  page.
- Text only; no attachments.


14. RLS MODEL
-------------
authz.thread_side derives the caller's side on every call:
- the worker of the thread while active;
- agency message.view / message.send;
- the linked facility's capabilities through the relationship.

There are no write grants; immutability is enforced by trigger. Revocation
is automatic.


15. WORKER MESSAGING
--------------------
- More → Messages (unread badge).
- Shift Details → Message agency.
- All / Unread list; thread with a context card (→ Shift Details), bubbles
  and pagination.
- Sticky composer: idempotent, offline-honest.


16. AGENCY MESSAGING
--------------------
- "Messages" in the workspace navigation (message.view).
- Conversations list and thread.
- Message worker from the worker record and from assigned workers on a
  shift; Message facility from the shift.
- Finance has no access.


17. FACILITY MESSAGING
----------------------
- Facility admin / scheduler: Messages in the navigation; "Message agency"
  from a staffing request.
- They see only their relationships' facility threads, and the agency by
  organisation name.
- The supervisor has no access.


18. UNREAD / READ BEHAVIOUR
---------------------------
- Per-thread unread counts and a total.
- Opening a thread marks it read and refreshes the badges.
- Sending marks your own message read.
- No typing, presence or delivery receipts.


19. RETENTION
-------------
Indefinite: no deletion path; history survives shift completion, request
closure, relationship end and access loss. No HIPAA claim.


20. NOTIFICATION INTEGRATION
----------------------------
- message_received goes to the worker when the agency side writes: "You
  have a new Chelth message regarding your shift", with no body and a deep
  link to the thread.
- One open notice per thread.
- Staff: in-app unread only (v1).
- Push is deferred.


21. PWA BEHAVIOUR

- Manifest, icons, static-only service worker, offline page, install entry

- Messaging and shift routes work in standalone mode.
- No message content or sensitive data in caches or browser storage

32. DEPLOYMENT SEQUENCE
-----------------------
1. Review the diff, commit E9-3B, E9-3C and E9-3D (stage explicitly), and
   open a PR.
2. Take a production backup / restore point.
3. Operator: supabase db push (dry run first; expect exactly the three
   migrations).
4. Merge to main, so Vercel deploys the app. The DB first and the app
   second is safe: the old app ignores the new columns, but the new app
   needs the new RPCs.
5. Smoke test:
   - worker sign-in → My Shifts → Shift Details → Message agency;
   - agency reply → worker unread;
   - facility "Message agency";
   - facility photo upload;
   - manifest and service worker.
6. Confirm the E9-2 scanner configuration is live.
7. Run the Android and iOS checklists (§28 / §29) and record the results.


33. REMAINING GAPS
------------------
- Real-device certification (Android, iOS).
- Facility images are not malware-scanned (accepted, documented).
- Staff are not e-mailed per message (in-app unread only); push is
  deferred.
- No worker ↔ facility direct messaging (by design, S1 D5).
- Facility projections do not show the unit; offers show no address before
  acceptance.
- Timesheet notes are not supported (no column; weekly submission).
- The owner cannot see quarantined documents after reload (RLS, E9-3C).
- Message retention is indefinite; any future purge needs an audited
  operator policy.
