1. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
Status: COMPLETE — every completion-gate criterion is met (section 23).

Chelth's first healthcare-specific data layer is in place, built on the S2
identity/authorization model without replacing it:

  - Workers are PEOPLE with per-agency engagement records:
    profile → agency membership → agency_workers. One person, many agencies,
    no identity duplication; tenant ownership is structurally enforced by
    composite FKs (safe even if RLS failed).
  - Client facilities (agency_facilities + facility_locations with explicit
    timezones) are distinct from facility ORGANISATIONS; a client record can
    be linked once, explicitly and verifiably, to a real facility organisation
    without duplicating history.
  - Agency ↔ facility relationships are first-class, with a lifecycle, ready
    for contracts/rates/VMS as attached child tables.
  - Cross-organisation access has exactly one primitive,
    authz.has_relationship_capability: specific relationship → specific
    resource → explicit policy. Linked facilities see their relationship and
    the agency's name — nothing else of the agency tenant.
  - 8 least-privilege domain capabilities; healthcare workers hold none (self
    access is an identity rule).
  - Invitation email: provider abstraction (Resend adapter, disabled by
    default), post-commit delivery with the outcome recorded on the invite.
  - Document storage: design only; no bucket exists.

Verification: 283 pgTAP assertions (99 new), 35 integration tests (12 new),
42 E2E tests on desktop + mobile (4 new flows × 2 viewports; 2 intentional
skips), 124 unit tests. All CI jobs reproduced locally with CI settings.

3. WORKER DOMAIN MODEL (docs/architecture/WORKFORCE_DOMAIN_MODEL.md)
--------------------------------------------------------------------------------
- Composite FK (membership_id, agency_organisation_id, profile_id) →
  memberships; (agency_organisation_id, 'agency') → organisations. An Agency A
  record cannot reference an Agency B membership, a different person, or a
  facility organisation (tested as owner role).
- Lifecycle: onboarding → active ⇄ inactive/suspended → terminated (terminal).
  Activation sets start_date; termination sets end_date. Re-engagement creates
  a new record; at most one non-terminated record per membership.
- worker_reference: agency's own reference, unique per agency (case-insensitive).
- Ownership columns immutable. No credentials, government identifiers or
  employment type stored (deferred by design).

4. FACILITY DOMAIN MODEL (docs/architecture/FACILITY_DOMAIN_MODEL.md)
--------------------------------------------------------------------------------
- agency_facilities: agency-owned (type-checked), name, facility type
  (reference table), status active|inactive|archived, REQUIRED IANA timezone
  (validated against Postgres' catalogue), business site phone/email,
  address, ISO country code, agency reference (unique per agency).
- linked_facility_organisation_id: NULL until linked; type-checked facility;
  set once, never re-pointed (trigger); one record per facility org per agency.
- facility_locations: bound to (facility, agency); explicit timezone (copied
  from the facility when omitted); unique names per facility; composite keys
  ready for departments and shifts. Departments designed, not created.
- Facility types as reference data (labels, retirement, drift test);
  lifecycle states as enums. Documented choice.

5. AGENCY-FACILITY RELATIONSHIP MODEL
   (docs/architecture/AGENCY_FACILITY_RELATIONSHIPS.md)
--------------------------------------------------------------------------------
- Relationship between the agency and its client record (optionally linked to
  a facility organisation). Lifecycle pending → active ⇄ suspended → ended;
  ended is immutable history; one open relationship per client record.
- Future contracts, rate cards, staffing permissions, facility-managed access
  and VMS attach as child tables keyed (relationship_id, agency_organisation_id).
- Linking today: platform-verified RPC (AAL2, audited in both organisations).
  Planned self-service: two-party consent link code (documented §5).
  Never automatic; never by name/email matching.

7. WORKER SELF-ACCESS
--------------------------------------------------------------------------------
- RLS: a worker reads own agency_workers rows only while that membership is
  live (authz.is_own_active_membership: active membership, active profile,
  non-archived organisation).
- Worker-visible: every column of agency_workers (by design all safe: status,
  reference, dates). Agency-internal data lives in separate tables.
- Worker may NOT: change status or reference (no capability; and nobody may
  change their own record); see notes (including notes about themselves even
  if they hold worker.notes.view); see other workers; see facilities.
- UI: "My worker record" on the organisation page.

8. RLS ARCHITECTURE
--------------------------------------------------------------------------------
  agency_workers            worker.view in the agency OR own live membership
  agency_worker_notes       worker.notes.view AND not about oneself
  agency_facilities         facility.view in the agency
  facility_locations        facility.view in the agency
  agency_facility_rel.      relationship.view in the agency OR
                            has_relationship_capability(id, 'relationship.view')
  facility_types            authenticated (reference)
All tables: SELECT-only grants to authenticated; writes via RPCs only;
nothing for anon; platform admins have no RLS path (tested).

9. CROSS-ORG SHARING MODEL (docs/security/CROSS_ORG_DATA_SHARING.md)
--------------------------------------------------------------------------------
Rule: specific relationship → specific shareable resource → explicit policy.
Primitive: authz.has_relationship_capability(relationship, capability) — true
only for a non-ended relationship whose client record is explicitly linked to
the caller's facility organisation AND the caller holds the capability there.
Shared today: the relationship row; agency name/status/start via
list_partner_agency_relationships(). Not shared: client records, locations,
notes, workers, worker profiles, agency organisation row/members.
Revocation is immediate (relationship ended, membership suspended/revoked,
profile/organisation suspended). Future shares (shifts, assigned workers,
timesheets, invoices, credential visibility) have documented templates.

12. WORKER ONBOARDING FLOW
--------------------------------------------------------------------------------
A worker record is created by the database whenever a membership is granted
agency.healthcare_worker (trigger), so every path obeys one rule:
  B (built)  Workforce → Invite worker: invitation with the role FIXED
             server-side; invitee signs up/verifies; acceptance grants the
             role; record created (onboarding). E2E-tested end to end.
  A (built)  Existing agency member: assign the Healthcare Worker role.
  A′         Existing Chelth identity outside the agency: invitation (no
             lookup/enumeration of other people).
  C          Candidate → worker: deferred to recruiting.
No auth users are ever created by the application.

13. TRANSACTIONAL EMAIL ARCHITECTURE (docs/architecture/TRANSACTIONAL_EMAIL.md)
--------------------------------------------------------------------------------
Decision: post-commit delivery with recorded outcome (not an outbox).
  commit invite+audit → send (raw token only in memory) → record
  delivery_status/provider/message id/error code → UI shows "emailed", or the
  link once if skipped/failed.
Why not an outbox now: it would require storing the raw token (secret at
rest) or a privileged cross-tenant worker. Outbox planned for secret-free
notifications. Guarantees: no email for rolled-back invites; failures never
silent (stored + shown + logged by code); resend rotates token and retries;
provider idempotency key per rotation.
Abstraction: src/lib/email (interface, disabled default, Resend adapter with
timeout and error codes, never throws, never logs recipients/links/bodies);
domain depends only on the interface. HTML escaping of all interpolations.
Resend recipient is read from the database, never the form.
Config: EMAIL_PROVIDER (disabled|resend), RESEND_API_KEY, EMAIL_FROM —
validated; resend without both fails build/start; key covered by bundle scan.
Operator steps remaining: Resend account + verified sending domain
(SPF/DKIM/DMARC), sending-only key in Vercel, disable click/open tracking,
Supabase custom SMTP when plan allows, minimal provider log retention.

19. SECURITY FINDINGS
--------------------------------------------------------------------------------
Review scope (all required topics): worker identity duplication; cross-agency
worker access; worker self-escalation; internal-note leakage; facility-client
enumeration; facility-organisation linking abuse; cross-org IDOR;
relationship-state bypass; revoked relationship access; status tampering;
invitation token leakage via email; provider logging; public storage;
service-role exposure. Each is covered by structural constraints and tests
(sections 10, 16, 17). No HIGH or CRITICAL issue open.

Findings fixed during the stage:
  F1 (Medium) Resend of an invitation took the recipient from the form. A user
     with invite authority could have sent a rotated link to an arbitrary
     address. Fixed: the recipient and role are read from the database.
  F2 (Low) Supabase CLI writes telemetry errors to stdout, which corrupted
     generated types. Fixed: scripts/generate-db-types.mjs (also used by CI).
  F3 (Low) The shared invite-link component was reachable only through a
     server-only feature index. Moved to src/components/shared (boundary
     preserved).

Accepted residual risks (Low):
  R1 A user with invite authority can record a false delivery status
     (operational metadata only; no access effect).
  R2 Revoking a worker's membership does not change their worker status.
     Access ends immediately; operational status stays with the agency.
  R3 Linking relies on platform-admin verification until two-party consent
     is built (audited in both organisations).
  R4 Email provider may retain message content per its retention policy
     (operator: minimise retention, disable tracking).
