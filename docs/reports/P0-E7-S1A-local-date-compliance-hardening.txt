CHELTH — P0-E7-S1A LOCAL-DATE COMPLIANCE EFFECTIVENESS HARDENING
Stage report · 2026-10-01 · branch p0-e7-s1a-local-date-compliance (uncommitted)

Narrow hardening patch. No payroll, invoicing, pricing, UI redesign or
unrelated refactor.

======================================================================
1. ROOT CAUSE
======================================================================
Audit of the full path before any change found four places where the
database's UTC calendar decided requirement effectiveness:

  1. credential_requirements.effective_from: `not null default
     current_date` (migration 20260930110300, line 108).
     create_credential_requirement had no date parameter and never
     supplied one, so every requirement started on the UTC date. The UI
     form had no date field and the server action sent none.
  2. update_credential_requirement deactivation set
     effective_until = current_date, which is also UTC.
  3. The readiness "today" views defaulted to the UTC date:
       - evaluate_worker_compliance and worker_readiness used
         p_as_of default current_date;
       - list_shared_worker_compliance (facility-facing) passed
         current_date.

The canonical comparison is correct. internal.evaluate_compliance checks
effective_from <= p_as_of <= effective_until, and assignment eligibility
passes each facility-LOCAL shift date (20260930120400 line 123).

So a requirement created in the US evening (after midnight UTC, before
local midnight) started on the UTC "tomorrow". It was not in force for
that local day's shifts.

Timezone availability:
  - Facilities, locations and shifts have IANA timezones.
  - Organisations (agencies) have NONE.

======================================================================
2. PREVIOUS BEHAVIOUR
======================================================================
Example: at 20:00 in Chicago on day D, it is 01:00 UTC on D + 1.

  - A facility requirement created at that moment got effective_from =
    D + 1.
  - A shift on local day D was evaluated on D, so the new requirement did
    not apply.
  - Deactivation recorded the UTC date as the last day.

This was reproduced in P0-E7-S1, when two attendance assertions failed
just after midnight UTC on committed code.

======================================================================
3. NEW DATE SEMANTICS
======================================================================
Requirement effective_from and effective_until are explicit calendar
DATES chosen by the caller.

  - The database has no default.
  - The create API requires p_effective_from (CH400 if null; plausible
    range 2000–2099).
  - Deactivation requires p_effective_until (on or after
    effective_from). It is refused when not deactivating.
  - Values cross the API as YYYY-MM-DD strings. They are never converted
    to instants, and the browser locale cannot change them: the date
    input's value is posted unchanged and validated as an ISO date.

UTC current_date no longer determines when any new requirement applies.

======================================================================
4. FACILITY-SCOPED REQUIREMENTS
======================================================================
The facility page defaults "Effective from" to the facility's local date,
computed deterministically from the facility's IANA timezone
(localCalendarDate). The field is visible, editable and labelled
"Defaults to today at <facility> (<timezone>)".

  - "Deactivate" defaults "Last day it applies" to the same local date.
  - The stored value remains a DATE.
  - The timezone is the facility's own, and the facility must belong to
    the agency (CH403 otherwise).

======================================================================
5. AGENCY-WIDE REQUIREMENTS
======================================================================
Chelth has no trustworthy agency timezone, so no default is derived.

  - The baseline form shows "Effective from" EMPTY and required, with the
    hint "Choose the calendar date it applies from. Each shift is checked
    against its facility's local date."
  - The API refuses a missing date (CH400).
  - There is no form of the function without a date (42883).
  - Deactivation on the agency page requires a chosen last day.

======================================================================
6. DATABASE CHANGES
======================================================================
Migration 20261001110000_local_date_requirements.sql:

  - Drops the default on credential_requirements.effective_from (stays
    NOT NULL).
  - create_credential_requirement(org, type, p_effective_from date
    [required, 3rd], facility, discipline, …). The old signature is
    dropped.
  - update_credential_requirement(…, p_effective_until date default
    null). Required when deactivating. The old signature is dropped.
  - New helpers:
      * internal.local_date_at(timezone, instant): pure;
      * internal.compliance_as_of(as_of, facility): explicit date, else
        facility-local today, else UTC (agency-wide display only).
  - evaluate_worker_compliance and worker_readiness: p_as_of default
    null, resolved through compliance_as_of. list_shared_worker_compliance
    uses the facility's local date.
  - Audit metadata now includes effective_from and effective_until (dates
    only).
  - Authorization and capabilities are unchanged:
    credential.requirements.manage at AAL2.

======================================================================
7. COMPLIANCE ENGINE VERIFICATION
======================================================================
internal.evaluate_compliance was NOT changed or duplicated.

  - Assignment eligibility still evaluates each facility-local shift date.
  - Proven by pgTAP case I and the integration test: a Chicago 20:00–23:00
    shift on D (UTC D + 1) ignores a requirement effective D + 1 and
    applies one effective D.
  - The engine excludes inactive requirements for all dates (status gate).
    effective_until is the recorded last day.

======================================================================

    pre-filled on facility pages, required and empty on the agency

  - The requirements list shows "From <date>[ to <date>]", formatted

  - "Deactivate" is now a small disclosure with "Last day it applies".
  - No redesign: existing components, brand tokens and layout.

9. HISTORICAL DATA TREATMENT
======================================================================
Existing credential_requirements rows were NOT rewritten. Dates produced
by the old UTC default remain as historical facts: there is no evidence
they are corrupt, only that they may be one day later than a local-date
choice would have been.

This stage changes future creation and deactivation only. pgTAP F checks
that later edits never change effective_from.

16. REMAINING RISKS
======================================================================
  - Agency-wide "readiness today" views with no facility still evaluate
    on the UTC date. This is display only: assignment always uses
    facility-local dates. It is documented, because Chelth has no agency
    timezone. Adding a canonical agency timezone (or always passing an
    explicit date) would remove it.
  - Historical requirements created under the old default may start one
    day later than intended. They were deliberately not rewritten; an
    agency can create a corrected requirement if needed.
  - Other date fields elsewhere (credential issue and expiry dates,
    "today" checks such as issue-date-not-in-future) still use
    current_date. They were outside this narrow stage, and none decides
    requirement effectiveness.
