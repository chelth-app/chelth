2. EXISTING NOTIFICATION / ATTENTION DATA SOURCES FOUND
-------------------------------------------------------
a) internal.notification_outbox
   (supabase/migrations/20260930120200_shift_assignments.sql and
   20260930130200_notification_delivery.sql)
   - What it is: the transactional EMAIL delivery queue. One row is one
     event for one recipient profile.
   - Columns: event, organisation, recipient profile, audience
     organisation, subject_type / subject_id, small detail jsonb.
   - Delivery fields: state (pending / processing / retry / sent / failed),
     attempts, claim lease, provider message id, last_error_code,
     deliver_until.
   - Event vocabulary: 23 events in src/lib/notifications/vocabulary.ts
     (mirrored from the database enum). The events enqueued by current
     migrations are:
     - assignment: worker_assigned, assignment_cancelled,
       assignment_declined, assignment_non_compliant;
     - shifts and requests: shift_offered, shift_cancelled,
       facility_request_submitted, facility_request_opened;
     - attendance: attendance_clock_in_blocked, attendance_clock_in_late,
       attendance_missed_clock_in, attendance_missed_clock_out,
       attendance_correction_requested, attendance_time_adjusted;
     - timesheets: timesheet_submitted, timesheet_rejected,
       timesheet_disputed, timesheet_facility_signoff_required;
     - pricing: pricing_blocked_missing_rate.
   - Why it is not usable:
     - it is in the internal schema, with RLS on and no grants to
       authenticated users; only the dispatcher role may claim or complete
       rows;
     - there is no read, unread, archived, acknowledged or resolved state;
     - display data is resolved only at claim time for email;
     - rows can be failed or expired (delivery mechanics, which §16 says
       must not be shown).
b) public.list_notification_deliveries(p_organisation_id, …)
   - An assignment.view delivery-health report for the WHOLE agency: every
     recipient's deliveries, with state, attempts and last_error_code.
   - Already shown as "Notifications not delivered" on Operations.
   - Not a per-user inbox, and it exposes exactly the delivery internals
     §16 forbids.
c) public.audit_events
   - The append-only audit log (action codes and identifiers only). It is
     not designed or permitted as user-facing notification content, and has
     no read state.
d) Authoritative attention read models: real, current, permission-gated,
   but not notifications.
   - Operations:
     - assignments needing attention (listAssignmentReadiness);
     - upcoming work under inactive relationships;
     - undelivered notifications.
   - Attendance: open exceptions, pending correction requests.
   - Timesheets: submitted / returned / disputed / awaiting facility, with
     history events and timestamps.
   - Compliance: readiness-engine results (expiring, missing, awaiting
     verification). These are states, not events, with no event timestamp.
   - Staffing requests and shifts: facility-requested shifts.

Conclusion: Chelth has no notification read model. There is no
user-scoped, readable list of events with read or archive state.

22. REMAINING FUNCTIONAL GAPS / OPTIONS FOR DECISION
----------------------------------------------------
To build the Notifications reference truthfully, the product needs one of
these.

A. In-app notification read model (the full reference)
   - Requires a migration and an explicit feature approval. It is outside
     this presentation-only stage.
   - A per-recipient, RLS-scoped table, or a read-only RPC over the outbox
     rows where recipient_profile_id = auth.uid(). It would expose event,
     subject and created_at, and display data resolved under the caller's
     own permissions, never delivery fields.
   - It also needs read_at / archived_at columns and "mark read" /
     "archive" RPCs.
   - Resolution state stays in the source domain (attendance, credentials,
     timesheets), as the reference's data rules require.

B. Attention Centre over existing read models (no migration)
   - A new /notifications route that only aggregates the authoritative
     attention sources in 2d, each through its own loader and capability
     gate, and deep-links to the source record.
   - Honest limits:
     - no Unread / Archived / Mark-all-read;
     - "Today" / "This Week" only where the source has a real event time
       (timesheet history, exceptions, corrections);
     - credential items are states, not events.
   - DERIVATION-MAP §F6 still requires approval of a new route.

C. Restyle Operations as the attention centre
   - Apply the locked Notifications list-and-drawer treatment to the
     existing /operations page, as DERIVATION-MAP already maps it.
   - Keep the route and nav item ("Operations"); no Notifications nav item
     or bell.
   - No new route and no new data.

Recommendation: C now, because it is purely presentation over real data
and already sanctioned by the derivation map. A later, as a planned feature
with its own migration and security tests. B only if a new aggregate route
is approved before A exists.

ADDENDUM 2 — ACTUAL DESKTOP WIDTH CONSTRAINT (root cause and fix)
=================================================================
The first width correction (cap raised from 1536 to 1920 px) did not
solve the problem. It still centred a capped container.

Root cause
----------
Traced in the rendered DOM: walking up from the Workforce "Workers table"
region and measuring each ancestor's computed width, max-width, margins
and padding at 1440 / 1920 / 2560.

Exactly ONE element constrained the width, in every operational route:

  <div class="mx-auto w-full px-4 sm:px-6 max-w-[1920px]
       lg:pr-[19px] lg:pl-[30px] flex flex-col gap-5">
  = PageContainer size="wide" (src/components/layout/page-container.tsx),
    rendered by AppShell for every workspace page.

Its max-width (1536 px originally, then 1920 px) together with mx-auto
capped the content and centred it.
- Measured at 2560 with the 1920 cap: 213 px margin on each side.
- With the original 1536 cap, every window wider than about 1750 CSS px
  showed a growing empty field. That includes a 1920 / 2560 screen at
  browser zoom below 100%.

No other ancestor constrains width. All have max-width: none and 0
margins:
- AppShell grid (214px minmax(0,1fr)), the column div, <main>;
- the page wrapper (.chelth-locked), the content wrapper, the section;
- the panel card, DataTableRegion.
No route layout and no Tailwind `container` is involved. The other max-w
values in workspace pages are search-field widths only.

Fix
---
- PageContainer "wide" is now `w-full px-4 sm:px-6 lg:pl-[30px]
  lg:pr-[19px]`: 100% of the workspace, no max-width, no auto margins.
- The "default" mode (personal and public pages) keeps its centred
  max-w-6xl.
- Because every workspace route (Overview, Operations, Shifts, Attendance,
  Timesheets, Workforce, Facilities, Compliance, Rates, Pricing, Payroll,
  Invoices) renders inside AppShell, the single fix applies to all of
  them.
- No component styling, font, card size, scale or padding changed.
- Record and detail pages keep their reading measures (text-level
  max-w-2xl / 68ch). Their panels now also span the workspace on very
  wide screens, since they share the shell.

Measured after the fix (Workers table, right edge = viewport − 19 px):
  1440 → x 245–1420
  1920 → x 245–1900
  2560 → x 245–2540
  3440 → x 245–3420
