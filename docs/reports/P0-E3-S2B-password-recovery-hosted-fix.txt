1. SYMPTOM
--------------------------------------------------------------------------------
On the hosted deployment, clicking the password-reset email link lands the
user on the sign-in / create-account page instead of /reset-password.

2. DIAGNOSIS — A COMBINATION (hosted configuration + one app routing weakness)
--------------------------------------------------------------------------------
PRIMARY — hosted Supabase email template mismatch (configuration).
  The Chelth flow requires the "Reset Password" email to link to the app's
  server-side verifier:
      {{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=recovery&next=/reset-password
  The hosted project's template has not been replaced, or has drifted from
  this. Supabase's DEFAULT template links to {{ .ConfirmationURL }}, i.e.
  GoTrue /auth/v1/verify, which redirects to redirect_to (the Site URL,
  because the app passes no redirectTo) with a PKCE code.
  Reproduced against the local GoTrue with the default-template URL:
      303 → http://localhost:3000?code=<redacted>
  The Site URL root is the Chelth landing page, whose only actions are
  "Sign in" and "Create account": exactly the reported behaviour. The app
  never sees the token_hash, and Chelth deliberately does not exchange PKCE
  codes at "/" (see §5).

CONTRIBUTING — app route logic (code defect, fixed).
  /auth/confirm took the recovery destination from the email's `next`
  parameter and fell back to "/". A Chelth-style template missing
  "&next=/reset-password" (as in Supabase documentation examples) verified
  the token correctly and then also landed the user on the landing page.
  A recovery session has only one purpose, so its destination must not
  depend on the template.

NOT the cause:
  - Site URL / redirect allow-list alone: with the token_hash template the
    link is built from {{ .SiteURL }} and redirect_to is not used. An incorrect
    Site URL (e.g. localhost) would produce an unreachable link, not the
    landing page. It must still be correct (§4).
  - resetPasswordForEmail redirectTo: it is omitted, and correctly so. The
    Chelth template does not use {{ .RedirectTo }}. Adding redirectTo would not
    help with the default template either: GoTrue would append a PKCE `code`,
    which /auth/confirm rejects by design (§5).
  - Safe-redirect handling: correct. getSafeRedirectPath allows only
    same-origin paths; unchanged.
  - Recovery type handling: "recovery" is allow-listed and verified with
    verifyOtp; unchanged.

5. CODE CHANGE (smallest fix)
--------------------------------------------------------------------------------
src/app/auth/confirm/route.ts
  - type=recovery → always redirect to /reset-password after successful
    verification; `next` is ignored for recovery.
  - Other types: fallback destination "/app" instead of "/" (a verified user
    is signed in; "/" only offers sign-in/create-account).
Unchanged and not weakened: token_hash is required; verifyOtp runs
server-side before any redirect; failures → /auth/error; the type allow-list
still excludes magiclink/invite; getSafeRedirectPath still guards `next`.
Security effect: slightly stronger. A recovery session can no longer be
redirected anywhere else via `next`.
Deliberately NOT added: PKCE `code` exchange at "/" or /auth/confirm. It
would be a second verification path, and it fails across devices (the code
verifier cookie lives only in the browser that requested the reset). The
token_hash template is the supported design.
