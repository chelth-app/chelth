12. EXACT UPLOAD ROOT CAUSE
---------------------------
Production evidence, read-only aggregate SQL via the Supabase CLI, no
personal data:
- credential_documents in production: 0 rows. Documents are never deleted.
- One credential was created at 19:11:37 UTC and shared one second later.
  It was withdrawn at 19:12:45 UTC (68 s later), with its draft version
  still open.
- internal.rate_limit_counters has no "credential.upload" bucket.
  begin_credential_document_upload consumes that limit in the same
  transaction that inserts the document row. So no begin-upload call ever
  committed, and none failed after consuming the limit either.
- The last deploy (merge of PR #29) was at 18:35 UTC, before the attempt.
  A stale server-action ID is therefore ruled out.
- The scanner migration's trigger fires only on status updates, so it
  cannot block the insert. The scanner principal is registered (1), and the
  production scan queue is empty.

Conclusion (proven): the Android upload never reached the database. It
stopped in the browser or in startUploadAction before its RPC.

Defects found on that path (all reproduced and fixed):

a) Errors were swallowed. The old DocumentUploader used try / finally with
   no catch. Any thrown error — a network drop on mobile data, a server
   action that cannot be reached, an interrupted request — reset the
   spinner and showed nothing. The worker saw "nothing happened".

b) Over-strict client type check for mobile pickers. The upload required
   the browser's File.type to be exactly application/pdf, image/jpeg or
   image/png, and the name's extension to match. Android document
   providers can report:
   - an empty or generic type (application/octet-stream);
   - "image/jpg";
   - a display name without an extension (e.g. "1000012345").
   Each of these was refused before any network call.

c) A submitter trap. "Submit for review" (primary, prominent) sat beside a
   small outline "Upload" and the raw file input. Picking a file and
   tapping the strong button submitted without uploading. The database
   refused with CH409, shown as the generic "not allowed in the item's
   current state". The selected file was never sent.

d) The accept attribute listed MIME types only. Some Android providers grey
   out files they cannot map to a MIME type.

Not determinable without the device or browser logs: which of (a), (b) or
(c) the tester hit. The server logs no client-side refusal, and runtime
logs (Vercel) were not available to this session. The data proves the
failure was client-side, before the RPC, and all three causes are removed.
The Android real-device check (section 22) will confirm.


13. UPLOAD FIX
--------------
src/features/credentials/components/evidence-uploader.tsx (replaces
document-uploader.tsx):

Control:
- The native input stays in the DOM (sr-only, focusable, labelled), so
  Files, Photos and Camera are offered where the device supports them.
  Camera is not forced.
- The visible control is a branded label button: "Choose document" /
  "Replace" / "Upload a different file".
- accept = the three MIME types plus .pdf, .jpg, .jpeg and .png.

States and messages:
- Idle: "Upload evidence" / "PDF, JPG or PNG · up to 10 MB".
- Selected: the file name, the size and "Ready to upload". Primary "Upload
  evidence"; secondary "Replace".
- Uploading: "Uploading document…", with the button disabled and
  aria-busy.

Checks and safeguards:
- Pre-check checkDocumentFile() in src/lib/domain/credentials.ts (unit
  tested). It takes the type from the extension when the picker reports
  none, and names an extension-less file from its declared type.
- A contradicting extension, an unknown type, an empty file or one over
  10 MB is refused at selection, with a specific message. Nothing is sent.
- Every failure path is caught and shown: network, ticket, storage and
  completion.
  - Offline: "You're offline. Connect to the internet, then upload again."
    Nothing is queued.
  - Server content refusal: "This document cannot be used. Upload a
    different file."
- A double tap is guarded by an in-flight ref; the test proves one document
  row.
- The File object is held in state; the input is cleared only after it is
  read.
- Success is never client-only. "Document uploaded. Checking document…"
  shows only while the server still reports that document as checking.

The server and security path are unchanged:
- one-time signed upload ticket, private bucket;
- server size, magic-byte signature and SHA-256 verification;
- the scanner gate.

The server's extension check still runs, on the normalised name. The
stored bytes remain the authority.

15. SCANNER HANDOFF
-------------------
Documents are untrusted until the scanner decides (E9-2, unchanged).
Worker states:
- no document          → "Upload evidence" (and "Add evidence to
                          continue." in Review)
- upload_pending       → "Upload didn't finish" · "Upload the document
                          again."
- scanning             → "Checking document…"
- scanning, scan_failed → "We couldn't finish checking this document yet.
                          We'll keep trying."
- clean                → "Document ready"
- rejected / quarantined → "This document cannot be used. Upload a
                          different file."

While a document is checking, the record re-reads server state every 5 s
(bounded to about 3 min, paused when hidden or offline). So the outcome
appears without a reload.

RLS limitation, unchanged: the owner cannot read rejected or quarantined
documents. A quarantined file therefore leaves the page. When one that was
being checked disappears while the page is open, the worker sees "This
document cannot be used. Upload a different file." After a later reload,
the evidence simply shows "Upload evidence" again.

No provider, signature, internal code, storage path or signed URL is shown
(asserted).

18. SERVICE WORKER
------------------
public/sw.js, registered by src/components/pwa/service-worker-registration
.tsx:
- registered in production builds only;
- secure contexts only;
- scope "/";
- updateViaCache "none".

Behaviour:
- install: precaches only /offline.html, /offline.css and the logo SVG;
  then skipWaiting.
- activate: deletes older chelth-* caches, enables navigation preload and
  claims clients.
- fetch:
  - non-GET → untouched (server actions, mutations);
  - cross-origin → untouched (Supabase auth, storage, signed URLs);
  - navigations → network (with preload); on network failure, the static
    offline page. A page is never served from cache;
  - /_next/static/* (content-hashed) and /brand/chelth/* → cache-first;
    only complete same-origin 200 responses are stored, capped at 300
    entries;
  - everything else (RSC payloads, /api, /auth, data) → network, untouched.
- /sw.js is served with "Cache-Control: no-cache, no-store,
  must-revalidate" (next.config.ts).


19. CACHING POLICY
------------------
Cached: hashed JS / CSS / fonts under /_next/static, the canonical brand
files, and the offline page and stylesheet.

Never cached or stored:
- pages;
- credential documents and signed URLs;
- worker, attendance and timesheet data;
- auth responses and server-action / mutation responses;
- geolocation;
- agency, private or finance data;
- invite tokens.

Asserted in E2E:
- after using My Shifts, Timesheets, My Credentials and a record, every
  cached URL is same-origin and under /_next/static/, /brand/chelth/ or
  /offline.*, with no token or _rsc query;
- localStorage and sessionStorage hold no token, invite, signed-URL or
  credential keys.

Update behaviour: pages are always network-fetched, so a new deployment is
visible on the next navigation. Old hashed chunks are never stale (the hash
changes) and are pruned by the cap. The new worker activates without
reloading open pages, so there is no forced reload mid-mutation. An "Update
available" prompt is therefore unnecessary and was not built.
