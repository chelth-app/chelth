4. TERMINOLOGY EXPANSION
------------------------
One central dictionary (SPELLING_PAIRS, [en-US, en-GB]) in
terminology.ts:
  organization(s)/organisation(s), license(s)/licence(s),
  canceled/cancelled, canceling/cancelling, center(s)/centre(s),
  meter(s)/metre(s), authorized/authorised, unauthorized/unauthorised,
  authorization/authorisation, recognize/recognise, behavior/behaviour,
  labor/labour, color/colour, fulfillment/fulfilment,
  enrollment/enrolment, catalog/catalogue, gray/grey.

Matching rules:
- whole words, case kept (organization / Organization / ORGANIZATION);
- a word touching / _ - or a letter is never treated as prose, nor is a dot
  followed by a letter, so routes, URLs and keys (/app/organisations/…,
  organisation.manage, organisationId) are never respelled. Sentence
  punctuation ("…the organization.") is prose.

Context: "license" is used in Chelth only as a NOUN (a professional
credential), so the pair is noun-only. UK "license" (verb) does not occur.
If it is ever needed, it gets explicit copy, not a pair. "program"
(software) is deliberately not paired.

Explicit terms for components: terms.organization, terms.organizations,
terms.canceled, plus the License / Licence terms from 3F.

How it is applied, with no locale conditions in components:
- Source copy is written in AMERICAN English, the fallback / pilot
  locale. Anything not wrapped therefore defaults to American, never
  British.
- Server components: spell("…") reads the request's terminology, which is
  resolved once per request in src/lib/i18n/request-terms.ts. Every
  workspace page awaits it first via loadOrganisationPage(); the overview
  and personal pages await it explicitly.
- Shared label maps (shift / assignment / payroll / invoice statuses,
  cancellation reasons, audit and notification labels) are respelled at
  their 23 server render sites: spell(MAP[key]). Module-level constants are
  never spelled at import time (checked; the calendar legend applies spell
  at render).
- Client components: <TerminologyProvider> in the workspace, self-service
  and personal layouts, and useSpell() (src/lib/i18n/terminology-context.tsx;
  no server code in client bundles — the build verifies this).
- Signed-out pages (sign-up, invitation): the browser language
  (getDeviceTerminology), else en-US.

10. EXISTING CURRENCY MODEL (audit)
-----------------------------------
- There was no organisation currency.
- Currency (ISO 4217, FK to public.currencies: USD, CAD, GBP, EUR, AUD,
  NZD) is stored per RATE VERSION and snapshotted on priced timesheets,
  payroll batches, invoice drafts and both adjustment types.
- The pricing engine refuses mixed currencies in a timesheet
  (RATE_CURRENCY_MISMATCH).
- Money is integer minor units, formatted through Intl.NumberFormat by
  currency code (formatMoney). There is no symbol concatenation anywhere.
- The rate form defaulted its currency select to "USD".


11. ORGANISATION CURRENCY IMPLEMENTATION
----------------------------------------
Migration 20261011100000_organisation_currency (additive):
- organisations.default_currency (FK to currencies; NULL ⇒ not set);
- internal.organisation_currencies_in_use(org): distinct currencies of
  non-discarded rate versions, priced timesheets, payroll batches, invoice
  drafts and adjustments;
- public.get_organisation_currency(org) (organisation.view):
  default_currency + currencies_in_use;
- public.set_organisation_currency(org, code): organisation.manage
  (privileged ⇒ AAL2), CH400 for unknown codes or symbols, CHY22 when
  records use another currency, audited.
Effective currency, used to preselect new rates: the default, else the
single currency in use, else the language's suggestion.
App: getOrganisationCurrency / listCurrencies /
setOrganisationCurrencyAction; CHY22 ⇒ CURRENCY_IN_USE ("Currency can't be
changed because this workspace already has rates or financial records in
another currency.").
Rate and version forms preselect the workspace currency and say:
"Workspace currency: <code>. Rates are stored in the currency chosen here
and never converted." Amounts are still parsed by the existing exact
minor-unit parser.


12. LOCALE → CURRENCY SUGGESTION
--------------------------------
suggestedCurrency(): en-GB ⇒ GBP, otherwise USD. It is used only while a
workspace has no default and no financial records, and the form says
"Suggested from the workspace language. Save to confirm it."
Language and currency are separate columns, RPCs and saves:
- changing the language never changes the currency;
- changing the currency never changes the language (pgTAP).
- en-GB + USD and en-US + GBP are valid (pgTAP / E2E).


13. CURRENCY-CHANGE SAFEGUARDS
------------------------------
A. No financial records ⇒ the default may change freely.
B. Draft rate versions: a non-discarded draft counts as "in use", because
   activating it would create mixed currencies, which the engine cannot
   price. Discarding the draft frees the currency (pgTAP).
C. Active rates, priced, payroll, invoice or adjustment records ⇒ only
   that currency may be the default. Anything else is refused by the
   DATABASE (CHY22), not just the UI. The UI explains it plainly.
No FX: nothing is converted, fetched or recalculated (§10 — not
implemented, not required).


14. HISTORICAL FINANCIAL PROTECTION (verified)
----------------------------------------------
- pgTAP 300: after a refused switch, the USD rate still reads
  USD:3000:4200 ($30.00 never becomes £30.00). Neither setting function
  can write any financial table (checked from the function source).
- Integration (financial.test.ts, real priced timesheets, a payroll batch
  and an invoice draft):
  - per-currency totals of priced (pay / bill), payroll and invoice are
    identical before and after switching the language en-GB → en-US;
  - switching the currency to GBP is refused (CHY22);
  - confirming USD changes nothing.


15. MONEY FORMATTING
--------------------
Centralised in formatMoney(minor, currency) via Intl.NumberFormat with the
currency CODE: USD $1,250.00, GBP £1,250.00, EUR €1,250.00 (unit-tested).
Amounts are always the stored minor units. The number pattern is the
en-US pattern for all workspaces, which is identical to en-GB for these
currencies. See gaps for the en-GB "US$" disambiguation.
