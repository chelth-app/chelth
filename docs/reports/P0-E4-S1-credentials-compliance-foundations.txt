1. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
Status: COMPLETE — every completion-gate criterion is met (section 26).

Chelth can now decide, with evidence and reasons, whether a healthcare worker
is eligible — for an agency, for a specific client facility, and on a given
date. The four questions stay separate:
  person holds X          credentials + immutable versions + documents
  agency accepts it       append-only per-agency, per-version verification
  what is required        agency baseline + facility requirements
  is the worker eligible  DERIVED by one engine; never stored

Key properties:
  - Credentials are person-owned, shared with an agency only by explicit
    consent, and Agency B never inherits Agency A's verification.
  - Documents live in a PRIVATE bucket, arrive via signed upload URLs, are
    content-checked server-side, and are UNTRUSTED until a scanner clears them
    (no production scanner yet ⇒ production uploads cannot count — by design).
  - One helper drives both table RLS and Storage policies; tests prove they
    agree for every actor at every trust state.
  - Signed download URLs are minted only after an audited gate, live 60 s, and
    are never stored, rendered or logged.
  - Facilities see only readiness + reason codes for workers explicitly shared
    under an active relationship.

Verification: 428 pgTAP assertions (145 new), 44 integration tests (9 new,
including real Storage uploads, signed-URL expiry and cross-agency trust), 46
E2E runs on desktop + mobile (4 new), 128 unit tests. CI-equivalent runs of
all three jobs pass. Two real defects were found by the new tests and fixed
(section 22). No HIGH/CRITICAL issue remains.

3. CREDENTIAL TYPE MODEL (docs/architecture/CREDENTIAL_DOMAIN_MODEL.md)
--------------------------------------------------------------------------------
Types describe their own shape — category, scope (person | facility),
jurisdiction rule (none | country | subdivision), requires issue date / expiry
date / number / document / verification, renewable, validity_months (e.g. TB
screening 12 months from issue), active/retired. No profession-specific code.
Seeded: RN, LPN/LVN, CNA, BLS, ACLS, PALS, CPR, TB screening, background check,
drug screening, facility orientation. identity_work_authorization category
exists with no types (not yet allowed). Jurisdictions: ISO 3166-1/3166-2
reference rows with checked parent/level structure; international by data.

4. PERSON CREDENTIAL MODEL
--------------------------------------------------------------------------------
credentials (owner profile, type, jurisdiction, issuing body; active |
withdrawn; core immutable) → credential_versions (dates; draft → submitted |
withdrawn; sequential numbers assigned by the DB; one draft at a time;
submitted versions frozen) → credential_documents. Numbers live in
credential_identifiers (owner + reviewers only). "Expired" is derived, never
stored. No SSN or similar identifiers.

5. AGENCY SHARING MODEL (docs/security/CREDENTIAL_SHARING_MODEL.md)
--------------------------------------------------------------------------------
credential_shares binds (credential, same person's membership, agency) by
composite FK; created only by the owner, only for an agency where they are a
current worker with an active membership. Access requires an ACTIVE share AND
an ACTIVE membership AND a capability. Revocation is immediate and historical.
UX: "Share this credential with <agency>" checkbox, pre-ticked and explained
when adding a credential in that agency's area; "Stop sharing" on the page.

6. VERIFICATION MODEL
--------------------------------------------------------------------------------
credential_verifications: append-only events per (version, agency[, facility])
with outcome under_review | verified | rejected(+structured reason), actor
membership bound by composite FK to the SAME agency, and a monotonic sequence
(latest decision = highest sequence). Rules: requires credential.verify
(AAL2); credential must be shared with that agency; no self-verification;
only submitted versions; verified requires a CLEAN document when the type
needs one; facility-scoped types must name one of the agency's facilities.
Renewal = new version ⇒ never inherits an earlier decision. Agencies see only
their own decisions; the worker sees all.

7. CREDENTIAL DOCUMENT ARCHITECTURE (docs/security/CREDENTIAL_DOCUMENT_SECURITY.md)
--------------------------------------------------------------------------------
Private bucket; opaque generated path {profile}/{credential}/{version}/{document};
MIME + size enforced by bucket, DB constraints and server; extension must
match type; upload via one-time signed upload URL straight from the browser
(no file through Vercel); server downloads the stored object as the user and
checks actual size = declared ≤ 10 MiB and MAGIC BYTES, records SHA-256;
failures are rejected and their bytes removed. Downloads: audited gate RPC →
Storage re-checks the same helper → 60-second signed URL → immediate redirect
restricted to the Supabase origin. No UPDATE policy (no overwrite); raw SQL
deletes refused by Storage; only an owner's rejected upload can be removed.

8. MALWARE / TRUST STATE
--------------------------------------------------------------------------------
upload_pending → scanning → clean | quarantined | rejected (trigger-enforced).
Only clean documents count as evidence, can be verified, or can be opened by
reviewers. No API role can set clean. There is NO production scanner yet:
production uploads remain `scanning` and therefore cannot satisfy
requirements — never falsely labelled clean. Local/dev/test path:
`npm run dev:scan-documents` and tests/support/scanner.ts (local database
only; refuse other hosts). Planned integration documented (webhook/Edge
Function with an approved privileged role → scanning service →
internal.record_document_scan_result).

9. DOCUMENT VERSIONING
--------------------------------------------------------------------------------
Renewal creates version N+1 with its own dates and documents; versions,
documents, verifications and shares are never deleted or rewritten (triggers
refuse even the owner role; tested). The engine picks the best valid version,
so a verified, valid v1 keeps a worker compliant while v2 is reviewed; once
v1 expires, an unverified v2 does not inherit v1's verification (tested).

10. FACILITY REQUIREMENTS (docs/architecture/FACILITY_CREDENTIAL_REQUIREMENTS.md)
--------------------------------------------------------------------------------
One table, credential_requirements: agency baseline (facility NULL) or one of
the agency's facilities (composite FK); optional discipline; must_be_verified
(forced on when the type requires it); minimum_validity_days;
expiry_warning_days (default 30); jurisdiction; effective dates; active/
inactive (deactivated, never deleted); one active per scope/discipline/type.
Facility-scoped types (orientation) only at facility scope. Management:
credential.requirements.manage (AAL2), audited. UI: /compliance (baseline) and
the facility page. Future location/department/role scoping documented.

11. DISCIPLINE MODEL
--------------------------------------------------------------------------------
disciplines reference (RN, LPN/LVN, CNA, MA, HHA, PT, OT, RT);
agency_worker_disciplines per agency worker (composite FK; worker.manage; no
self-changes; audited). Used only to select applicable requirements.

12. COMPLIANCE ENGINE (docs/architecture/COMPLIANCE_ENGINE.md)
--------------------------------------------------------------------------------
internal.evaluate_compliance(worker, facility?, as_of) — the single evaluator
behind evaluate_worker_compliance, worker_readiness and the facility
projection. Evaluates applicable requirements (baseline + facility, effective
on as_of, discipline-matched) against credentials shared with THIS agency,
using this agency's latest decision per version, document trust, and dates
(effective expiry = expiry_date or issue + validity_months; valid through the
expiry date). Best candidate version wins by rank. Readiness: blocking ⇒
not_eligible; warnings only ⇒ action_required; else ready. `as_of` supports
shift-date evaluation later. Nothing is stored.

14. FACILITY CREDENTIAL VISIBILITY
--------------------------------------------------------------------------------

relationship, created with credential.verify under an ACTIVE relationship.
list_shared_worker_compliance(relationship): linked facility members with

15. RLS ARCHITECTURE
--------------------------------------------------------------------------------
  credentials / versions        owner OR can_access_shared_credential(…, 'credential.view')
  credential_identifiers        owner OR …'credential.review' (AAL2)
  credential_documents          can_read_credential_document (owner non-rejected; reviewer clean)
  storage.objects (bucket)      SAME helper via can_read/upload/delete_credential_object
  credential_shares             owner OR credential.view in that agency
  credential_verifications      owner OR (credential.view in that agency AND active share)
  credential_requirements       credential.requirements.view
  agency_worker_disciplines     worker.view OR compliance.view OR own worker record
  relationship_worker_…_shares  compliance.view (agency); facilities via projection only
  reference tables              authenticated read
No policy relies on bare membership. Platform admins have no path (tested).
authenticated holds SELECT only; all writes via RPCs (baseline pgTAP).

16. STRUCTURAL INTEGRITY

  share ↔ same person's membership ↔ agency composite FK (membership, org, profile) + agency type

  verification facility ↔ same agency       composite FK (facility, org)
  requirement facility ↔ same agency        composite FK (facility, org); agency type

  immutability / append-only                triggers on credentials core, identifiers,

                                            requirements (no delete), compliance shares
  trust state machine                       trigger-enforced transitions

22. SECURITY FINDINGS
--------------------------------------------------------------------------------
Reviewed: credential ownership confusion, multi-agency leakage, verification
trust boundaries, self-approval, number exposure, document access leakage,
signed URL leakage, storage/table mismatch, malware-state bypass, history
overwrite, expired false-positive, facility over-sharing, requirement
tampering, stale verification after renewal, revoked membership, revoked
relationship, service-role exposure — each covered by constraints and tests
(sections 15–21). No HIGH or CRITICAL issue open.

Defects found and fixed in this stage:
  F1 (High, fixed) Latest-verification ambiguity: "current decision" was
     chosen by created_at; events in one transaction tie, so a later
     `verified` could lose to an earlier `rejected` (or vice versa). Fixed
     with a monotonic sequence (unapplied migration amended). pgTAP covers it.
  F2 (Medium, fixed) Server env variable NAMES (e.g. RESEND_API_KEY) reached a
     browser chunk once a client component imported the browser Supabase
     client (env.public → env.schema also held the server schema). Found by
     the bundle scanner; fixed by splitting env.server.schema.ts.
  F3 (Info) Local environment: after the repository was linked to the hosted
     Chelth project (supabase/.temp, git-ignored; ref for "chelth-Project",
     no Maaklin reference), the CLI pinned storage v1.77.5 while an older
     v1.61.7 container was still running and failed uploads (42P10). Resolved
     by restarting the local stack. No hosted resources were touched.

Accepted residual risks:
  R1 (Medium) No production malware scanner: production uploads cannot become
     evidence until one is integrated (fail-safe, but blocks go-live of
     credential verification).
  R2 (Low) complete_credential_document_upload trusts the caller's
     content-check flag; forging it only moves a document to `scanning`
     (still untrusted).
  R3 (Low) A reviewer can keep a document they downloaded; access is audited.
  R4 (Low) Expiry uses UTC dates; facility-local dates arrive with shifts.

23. KNOWN LIMITATIONS
--------------------------------------------------------------------------------
- Production scanning not integrated (R1).
- Headless browsers treat the PDF as a download; real browsers open it.
- Readiness per facility is shown via a picker on the worker page (no bulk
  readiness board).
- Credential numbers are shown in full to reviewers (masking/redaction UX later).
- Requirement editing is deactivate-and-re-add (plus RPC-level updates of
  validity/verification fields).
- CI pins Supabase CLI 2.109; local linked environment pins newer service
  versions — keep CLI and images aligned when upgrading.
