2. PASSWORD-CONTROL IMPLEMENTATION
----------------------------------
New: src/components/ui/password-input.tsx (PasswordInput, client).

- Wraps the existing Input. FormField's id, required, invalid and
  aria-describedby are forwarded to the real input. name, autocomplete,
  validation and value handling are unchanged.
- Hidden by default (type="password"). The toggle switches type password
  ↔ text and the typed value is kept (asserted).
- The toggle:
  - is a type="button", so it never submits (asserted: the URL is
    unchanged and no form alert appears);
  - keeps the caret in the field when clicked with a pointer
    (onMouseDown preventDefault);
  - is a 44 px-wide hit area inside the field's right edge;
  - adds right padding (pr-12) so text never collides with it;
  - looks subtle: slate-500, navy on hover, inset focus ring, no button
    chrome;
  - causes no layout shift, and the field stays at the locked 44 px
    control height.
- Icon: eye / eye-off as inline SVG in the existing line family (1.9
  stroke, round caps). No icon library was added.
- Visibility is component state only: never stored, logged or persisted,
  and reset on navigation.


3. ACCESSIBILITY BEHAVIOUR
--------------------------
- The accessible name comes from screen-reader-only text that reflects the
  state: "Show password" / "Hide password" (and "new password" / "confirm
  password" on reset).
  - This is deliberately not an aria-label, so label lookups for the field
    itself ("Password", "New password") stay unambiguous for assistive

- aria-controls points to the input.
- Keyboard: the toggle is in the tab order; Enter / Space toggles it; focus
  stays on the toggle and its name updates (asserted).
- Visible focus: an inset ring inside the field, never clipped.
- axe (wcag2a / 2aa / 22aa) is clean on sign-in and sign-up after
  toggling.


4. SCROLLBAR ROOT CAUSE (measured, not assumed)
-----------------------------------------------
Computed layout of a SectionTabs row on desktop:
- overflow-x: auto;
- overflow-y: auto (CSS forces overflow-y to auto when overflow-x is not
  visible);
- scrollHeight 44 against clientHeight 43.

Each tab link has a −1 px bottom margin so the active underline overlaps
the divider. That makes the content 1 px taller than the row, so the row is
vertically scrollable by 1 px. On platforms that always show scrollbars
(for example macOS with a mouse, or Windows), the browser draws a thin
vertical scrollbar at the right edge even when the tabs fit. Headless
Chromium uses overlay scrollbars, which is why earlier captures never showed
it.


5. SHARED SECTIONTABS CHANGES
-----------------------------
File: src/components/ui/section-tabs.tsx (fixed once, inherited
everywhere).

- overflow-y: hidden. The row can no longer scroll vertically, so the
  right-edge artifact is gone. The 1 px overlap was already clipped by the
  same box, so the underline looks the same.
- overflow-x: auto is kept, so horizontal scrolling still works by touch,
  trackpad, wheel and keyboard focus.
- The horizontal scrollbar chrome is hidden (scrollbar-width: none and
  ::-webkit-scrollbar hidden).
- Focus rings are drawn inset (outline-offset −3 px, 6 px top radius). This
  is the approved Finance treatment, applied globally because hidden
  overflow-y would otherwise clip outset rings into vertical bars on every
  tab row. It is the same treatment as Finance, with no spacing or size
  change.
- Tab structure, labels, aria-current and the locked active treatment are
  unchanged. The Finance shell keeps its own identical classes (redundant,
  harmless; the locked shell is untouched).
