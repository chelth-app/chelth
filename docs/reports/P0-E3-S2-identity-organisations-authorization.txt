1. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
Status: COMPLETE — every completion-gate criterion is met (section 22).

Chelth now has a multi-organisation identity and authorization model:

  identity (profile) → memberships (one per organisation)
                     → role assignments (membership-scoped, history kept)
                     → capabilities (namespaced; privileged ones need MFA/AAL2)

Authorization is evaluated by Postgres on every request through one
primitive, authz.has_capability(organisation_id, capability), used by both RLS
policies and SECURITY DEFINER RPCs. All writes to identity/organisation
tables go through RPCs that authorise, enforce anti-escalation rules, mutate
and audit in a single transaction. Platform administration is a separate,
AAL2-gated, fully audited privilege with no RLS access to tenant data.
No service-role key is used anywhere — application, tests or CI.

Verification: 184 pgTAP assertions (7 files), 23 integration tests against
the real local Supabase APIs (real sign-up + email verification via Mailpit,
real TOTP), 34 Playwright E2E tests on desktop and mobile viewports (2
intentional desktop-only skips), 84 unit tests. All three CI jobs were
reproduced locally with CI's exact service configuration and passed.

No healthcare domain modules were built. Nothing was committed or pushed.

3. IDENTITY MODEL
--------------------------------------------------------------------------------
- Supabase Auth is the identity source; profiles.id = auth.users.id.
- Profile created by trigger; only a sanitised display_name is read from
  (user-controlled) metadata. Email stays in auth.users (PII minimisation).
- Users may update only their own display_name (column grant + RLS).
- profiles has NO role / organisation / active-organisation column
  (pgTAP columns_are test).
- A suspended profile holds no capabilities anywhere.
- Sign-up model: sign-up creates an identity ONLY. No automatic role in any
  organisation. People join by invitation or explicitly create an agency.

4. ORGANISATION MODEL
--------------------------------------------------------------------------------
- Constrained type enum (agency | facility); immutable (trigger).
- Stable slug; self-serve slugs get a random suffix (non-enumerable).
- Status active | suspended | archived; never deleted.
- Creation paths:
    create_organisation('agency', …)  verified email, 5/day; creator's
                                      membership + owner role derived
                                      server-side, atomic, audited
    platform_create_organisation(…)   platform admin (AAL2); creates org +
                                      owner INVITATION; admin is not a member
  Facilities are not self-serve.

5. MEMBERSHIP MODEL
--------------------------------------------------------------------------------
- One membership per (organisation, profile); organisation_id/profile_id
  immutable.
- Lifecycle: active ⇄ suspended → revoked. Suspended: no access, roles kept.
  Revoked: all role assignments ended (re-admission by new invitation only,
  never silently restoring old privileges).
- Invitation state lives in organisation_invites (justified deviation from an
  "invited" membership status: invitees may not have an identity yet).
- Nobody can change their own membership. Managing a member requires
  membership.manage AND holding every capability the target holds.
- Multi-organisation identities verified in pgTAP (one identity: Recruiter in
  Alpha, Healthcare Worker in Beta, different capabilities per organisation).

6. ROLES & CAPABILITIES
--------------------------------------------------------------------------------
Capabilities (privileged = AAL2): organisation.view, organisation.manage*,
membership.view, membership.invite*, membership.manage*, role.assign*,
audit.view*.

Roles: agency.admin (owner), agency.operations_manager, agency.recruiter,
agency.scheduler, agency.credentialing_officer, agency.finance,
agency.healthcare_worker, facility.admin (owner), facility.scheduler,
facility.supervisor. Platform Admin is not a role (section 7).

Rules: code checks capabilities, never role names; role key namespace must
equal organisation type (constraint); one owner role per type; typed TS
vocabulary in src/lib/authz with an integration drift test against the DB.

Role assignment: role.assign (AAL2) + not self + capability ceiling (cannot
grant or revoke a role conferring anything the caller lacks) + role valid for
org type + active membership. Revocation sets revoked_at; rows can never be
deleted or un-revoked (trigger). Last-administrator protection.

Scoped permissions: documented evolution path (AUTHORIZATION_MODEL.md §10):
nullable scope columns on membership_roles + 4-argument has_capability.

7. PLATFORM ADMIN MODEL
--------------------------------------------------------------------------------
- platform_admins grant + AAL2 session (authz.is_platform_admin).
- Not a tenant member; RLS gives no tenant rows (tested).
- Narrow RPCs only; EVERY call (reads included) audited with the session AAL.
- Grants/revocations: internal.grant_platform_admin / revoke_platform_admin,
  executable only by the database owner role, audited with the named
  operator (DATABASE_MIGRATION_POLICY.md §11). Unreachable via the API.

8. MFA ENFORCEMENT
--------------------------------------------------------------------------------
Where AAL2 is checked:
  RLS / helper layer  authz.has_capability (privileged capabilities),
                      authz.is_platform_admin — authoritative
  RPC layer           internal.require_capability / require_platform_admin
                      raise CH402 so clients can prompt step-up — authoritative
  Server Actions      map CH402 → MFA_REQUIRED (no authority)
  UI                  my_capabilities().is_satisfied → step-up notice (hint)
AAL comes from the Supabase-signed JWT; a missing claim is treated as AAL1.
TOTP enrolment (/app/security) and step-up (/app/security/verify) are built.
Policy: MFA is required to exercise privileged capabilities; enrolment is not
forced on non-privileged users (e.g. healthcare workers).

9. RLS ARCHITECTURE
--------------------------------------------------------------------------------
- RLS enabled on every table in public/authz/internal (pgTAP).
- authenticated holds only SELECT at table level; the single direct write is
  UPDATE(display_name) on one's own profile (pgTAP asserts exactly this).
- anon holds nothing anywhere (pgTAP).
- Policies: profiles (self or co-member via membership.view), organisations
  (active member), memberships and role assignments (own or membership.view
  in that org), reference data (authenticated), platform_admins (own rows),
  audit_events (own actions or audit.view@AAL2 in that org), invites (none).
- Cross-tenant integrity is declarative: composite FKs
  (membership_id, organisation_id), (organisation_id, organisation_type),
  (role_key, organisation_type) on membership_roles and invites, plus
  immutability triggers. Tested to hold even for the owner role.
- No roles/capabilities in JWT claims → suspension/revocation are immediate.

11. INVITATION SYSTEM
--------------------------------------------------------------------------------
  strong token          256-bit pgcrypto, base64url (43 chars)
  hashed at rest        SHA-256 only; table has no API grants
  shown only as needed  returned once to issuer; never listed/logged/audited
  expiry / single use   7 days; pending → accepted under row lock
  resend rotates        new token, old hash overwritten, max 5 sends
  uniform pre-auth      NO anonymous validation endpoint; /invite/<token>
                        responds identically for every token and moves the
                        token into a 1-hour httpOnly cookie
  no PII in validation  preview returns organisation + role names only
  server-side accept    accept_organisation_invite(token) — token is the only
                        parameter; org and role come from the invite row
  email binding         caller's VERIFIED auth.users email must match
  throttling            20 attempts / identity / 15 min; invalid attempts
                        return an empty result (not an error) so the counter
                        and the failure audit event commit
  stale issuer          issuer must still hold membership.invite + the role's
                        capabilities (or platform admin) at redemption
  audited               created/resent/revoked/accepted/acceptance_failed
Delivery: links are displayed once to the issuer; email delivery is deferred
(section 20).

12. AUDIT EVENT ARCHITECTURE
--------------------------------------------------------------------------------
Fields: id, occurred_at, actor_profile_id (no FK — outlives identities),
actor_membership_id (composite FK with organisation_id), actor_aal,
organisation_id, action (namespaced), target_type, target_id, metadata
(jsonb object ≤ 4 KB; identifiers/codes only), request_id (from the
x-chelth-request-id header the server forwards; accepted only if a UUID).
Append-only: no API write grants; triggers refuse UPDATE/DELETE/TRUNCATE for
every role including the owner. Written only by internal.record_audit_event
inside RPCs. Visibility: own actions, or audit.view (AAL2) per organisation.
Actions recorded this stage: organisation.created/status_changed,
membership.created/reactivated/status_changed, role.assigned/revoked,
invite.created/resent/revoked/accepted/acceptance_failed,
profile.status_changed, platform.admin_granted/admin_revoked/
organisations_listed.

18. SECURITY FINDINGS
--------------------------------------------------------------------------------
Review of privilege escalation, IDOR, cross-organisation access, stale
membership, suspended membership, revoked roles, invite replay/enumeration,
role tampering, AAL1 vs AAL2, RPC grants, audit tampering, profile
impersonation, anonymous access and service-role leakage:
docs/security/THREAT_MODEL_IDENTITY.md (30 threats, controls, tests,
residual risk). No open high/critical findings.

Residual risks accepted (documented, deferred):
R1 (Medium) Denied RPC calls are not audited in the database — Postgres rolls
   back the audit row with the raised error. Denials are logged by the
   Server Action layer; invitation failures are audited.
R2 (Medium) AAL2 lasts for the session; no "recent MFA" window for platform
   actions.
R3 (Low)    Hosting access logs may record /invite/<token> paths; tokens remain
   bound to the invitee's verified email.
R4 (Low)    A superuser can disable audit triggers; off-site immutable export
   deferred.
R5 (Low)    Suspended profiles can still authenticate (but hold nothing);
   Auth-level ban deferred.
R6 (Medium) Hosted Auth settings (templates, Site URL, rate limits, MFA,
   confirmations, exposed schemas) must be aligned manually with
   supabase/config.toml — release checklist in the threat model. Local
   config deliberately relaxes auth rate limits and the resend interval for
   tests (marked LOCAL ONLY).

Defects found and fixed during this stage:
D1 (S1 foundation) Root src/app/loading.tsx made notFound() pages return HTTP
   200 (streaming began before the 404). Removed; 404s are now real 404s.
D2 (S1 foundation) Label announced "required" twice (sr-only text + native
   required). Marker is now aria-hidden; the native attribute is announced.
D3 Members table scroll region was not keyboard-scrollable on mobile (axe
   scrollable-region-focusable). Now a labelled, focusable region.
D4 Dependabot opened failing PRs for pinned majors. Ignore rules added.
No secrets found (working tree and new files); no Maaklin references outside
this report; no service-role usage anywhere.
