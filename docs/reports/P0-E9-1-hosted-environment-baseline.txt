13. RELEASE-DISCIPLINE DOCUMENTATION (proposed model)
-----------------------------------------------------
This was not written into docs/ in this phase: it depends on the
environment decision in section 17.

Proposed, consistent with DATABASE_MIGRATION_POLICY.md:

  LOCAL
    - every change; format, lint, typecheck, unit, build, bundle scan,
      check:migrations;
    - db reset from zero, db lint, pgTAP, integration, Playwright (= CI).
  STAGING (new Supabase project + Vercel Preview / staging branch)
    - operator `supabase db push --dry-run` then `db push`;
    - record applied versions; read back Auth / Storage / cron;
    - Auth smoke test with a real mailbox;
    - golden-path and role smoke as phases progress.
  PRODUCTION (only after staging sign-off)
    - backup point confirmed (PITR or manual);
    - `db push --dry-run` reviewed, then applied by a named operator;
    - verified by a second person (`migration list`);
    - application deployed AFTER the schema (expand-first);
    - rollback = Vercel instant rollback of the app;
    - schema is fix-forward only (no down-migrations);
    - data loss = PITR restore incident.
  Promotion conditions:
    - CI green; staging migrations applied and verified;
    - staging smoke tests passed and recorded;
    - no open P0 / P1 for the change.
  Migrations stay operator-controlled. No automatic production DB
  migrations are proposed.
