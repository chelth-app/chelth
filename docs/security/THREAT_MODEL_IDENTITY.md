# Threat Model — Identity, Organisations & Authorization

Status: P0-E3-S2. Scope: authentication, profiles, organisations,
memberships, roles/capabilities, invitations, platform administration, audit.
Method: STRIDE-style review of each asset against the controls implemented in
this stage. "Test" references point to `supabase/tests/security/*.test.sql`
(pgTAP), `tests/integration/*` and `tests/e2e/*`.

## Assets

Tenant membership data · role assignments · invitation tokens · platform
privilege · audit history · session tokens · user email/PII.

## Trust boundaries

Browser ↔ Next.js server ↔ PostgREST/GoTrue ↔ Postgres. The browser and the
Next.js server are both **untrusted for authorization**: any authenticated
user can call every exposed RPC directly with their own JWT. The database is
the enforcement point.

## Hosted configuration that must match (release checklist)

- Email confirmation ON; secure password change ON; min length 12 with
  lower/upper/digit; anonymous sign-ins OFF; no OAuth providers.
- TOTP MFA enrol/verify ON.
- Email templates from `supabase/templates/` (Confirm signup, Reset Password,
  Change Email — never the defaults using `{{ .ConfirmationURL }}`); Site URL = the Chelth domain;
  redirect allow-list limited to `https://<domain>/auth/confirm`.
- **Production** rate limits (not the local test values): resend interval
  60 s; default sign-in/sign-up and token-verification limits.
- Data API exposed schemas: `public` only (GraphQL not exposed).

## Deferred mitigations

- Audit export to an immutable external store; alerting on
  `invite.acceptance_failed` / platform events.
- Database-level recording of denied RPC attempts.
- "Recent MFA" requirement (re-verification window) for platform actions.
- Supabase Auth ban for suspended profiles (currently: authenticated but powerless).
- Automated verification of hosted Auth configuration.
